## Trigger — re-based 2026-07-31

The original trigger was **shipping need**: build when a profiled real game shows the sim tick consuming more than ~half its 16.6 ms budget single-threaded. No game is anywhere near it (vigil's full-horde frame: ~1.8 ms).

The new trigger is **credibility need**. Determinism is the engine's most-contested pillar when presented: skeptics claim it is either too limiting for high-quality games or a burden that will be abandoned, and the single-threaded sim amplifies both claims. "Determinism forbids multithreading" is a falsifiable statement, and the strongest refutation is an artifact, not an argument: a real-workload scene whose sim runs in parallel with **bit-identical `WorldHash` sequences at 1, 2, and 8 threads**. The demonstration is the vertical slice; the engine's credibility is the product it ships in.

## Deliverable — the thing to show

- A stress scene built from **real vigil game systems at horde scale** — not a synthetic benchmark (an N-body toy proves nothing and skeptics would rightly call it a benchmark special).
- A live thread-count toggle (or CLI flag) with the `WorldHash` sequence displayed/verified identical across 1/2/8 threads.
- Honest numbers, Amdahl owned up front: "N× on the heavy systems, bit-identical results" — never "8× on 8 cores." Hashing, command drain, and extract stay sequential; a skeptic who finds the gap before we state it wins the room.
- The scene and its replay stay committed as a **permanent CI gate** — the artifact that keeps the claim true forever, not a one-off demo.

## Test oracle

`run_lockstep()` stays fully sequential forever as the reference implementation. The parallel driver must produce **bit-identical `WorldHash` sequences at any thread count**. The job system is never trusted, only diffed: CI replays a corpus of recorded sessions at 1, 2, and 8 threads and requires identical hash sequences. Thread count must never affect results; 1-thread parallel-driver output must equal lockstep output.

**No named replay corpus exists today** — the de-facto corpus is the per-game committed artifacts (`games/vigil/run.lrp`, `games/breakout/run.lrp`), each guarded by its game's `tests/replay.rs`. S1 creates the third and heaviest member (`games/vigil/stress.lrp`); J0 names the set and gates it at three thread counts. The stress scene exists *before* the machinery precisely so the oracle is honest from day one — a gate built against toy workloads passes trivially and guards nothing.

## Core principle

Parallelism is deterministic iff the observable result is independent of thread interleaving. Four rules, each a work item:

1. **Static partitioning** — entities split into fixed chunks by index. Work-stealing may schedule chunks, but chunk *boundaries* and *combination order* are fixed.
2. **Disjoint writes** — each chunk writes only its own entities' components; no shared mutable state.
3. **Ordered reductions** — float addition isn't associative; aggregates (summed forces, collision-pair lists, min/max) combine in fixed chunk order regardless of completion order. Pair lists concatenate in chunk order or sort by canonical key.
4. **Splittable RNG** — one shared `DeterministicRng` resource can't be pulled from concurrently. Use counter-based derived streams from `(seed, frame, entity)`.

## Current-code facts that shape the work

Verified 2026-07-31; file:line references are to that state of the tree.

**ECS / scheduling:**
- Systems are `fn(&mut World, &SystemCtx)` in registration order (`crates/ludion-ecs/src/schedule.rs:61`) — no declared read/write sets, so nothing can run concurrently with anything.
- **Typed queries already exist and are the sanctioned design** (`World::query`/`query_ids`, `crates/ludion-ecs/src/world.rs:353`/`406`; freeze list at `engine-architecture.md:169-187` names them in-scope). Vigil systems already use them as the dominant idiom. The real gap: `query` takes `&mut self`, so systems snapshot into a `Vec` then use per-entity `get`/`get_mut` mid-loop — and those per-entity accessors are **invisible to the query-drift verifier** (`L1126`/`L1127`), which only records `query`/`query_ids` shapes (`world.rs:418-437`).
- Storage is per-component BTreeMaps under `#![forbid(unsafe_code)]` — disjoint `&mut` chunks require dense columns. Entity id is `{index: u32, generation: u32}` (`crates/ludion-core/src/ids.rs:33`); storage keys are the bare index, which recycles — stream derivation must use `(index, generation)`.
- Existing determinism contracts (ascending-entity-index iteration, LIFO free list `crates/ludion-ecs/src/entity.rs:140`, registration-order registry) are exactly the invariants the runtime must preserve, and they're already tested.

**RNG:**
- `DeterministicRng` is PCG32 (PCG-XSH-RR 64/32) with `new_with_stream(seed, stream)` already present (`crates/ludion-core/src/rng.rs:77`) — but called nowhere outside its own tests. Caveat: the stream's top bit is discarded (`increment = (stream << 1) | 1`), so a 64-bit hash-derived stream silently collides on bit 63 — mask to 63 bits.
- The repo's one precedent for coordinate-derived (never draw-order) randomness is the map generator's `variant_pick(seed, row, col, count)` — a splitmix64 finalizer (`crates/ludion-scene/src/map.rs:1766`, rationale at `map.rs:29-31`). That is the shape to copy.
- Vigil's entire RNG surface is **five call sites in two files**: four in `spawner.rs` (archetype pick, pack anchor, position × retries) and one in `progression.rs:184` (level-up offer shuffle). Gore fragments, nav, everything else is already hash-pure by construction.
- RNG state is deliberately excluded from `WorldHash` (`crates/ludion-sim/src/hash.rs:39`); snapshots carry it separately.

**Profiling (this is where the S1 engine work lives):**
- Per-system sim timings exist (`SimProfile.systems`, medians) — but **only via the game binary** (`cargo run --release -p vigil -- --scene … --profile 120`); the `ludion profile` CLI verb uses the built-in registry and reports an empty system list (`crates/ludion-engine/src/profile.rs:57`).
- **Command drain, `WorldHash` hashing, and extract are measured nowhere.** The profile loop drives `advance_observed` directly (never `Engine::execute`), never hashes, and extracts **once** before the GPU loop then re-renders the same `RenderScene` (`profile.rs:223`, `:270-273`). `WorldHash` is only computed on explicit request, never per-tick in live play (`crates/ludion-engine/src/engine.rs:1113`).
- The timing seam is clean: `ScheduleObserver` (`schedule.rs:218`) is deliberately clock-free; `crates/ludion-engine/src/profile.rs` is the single sanctioned wall-clock site. `observer_does_not_change_world_hash` (`profile.rs:721`) already proves profiling is hash-neutral.

**Load generation (vigil):**
- `MAX_ENEMIES = 500` (`games/vigil/src/tunables.rs:222`) is Rust, not data — but it is a **spawner-side budget only**: it never culls pre-existing enemies. Scene-authored enemies bypass it entirely; when live count exceeds it the spawner just idles. This is exactly how the existing E6 gate reaches 500 (`scenes/budget-swarm.yaml`: 500 authored enemies + 300 bolts + 200 pickups, invulnerable player). The spawner also can't fill a horde in-run anyway (4 enemies / 2 s against a 180 s clock).
- ⚠️ `budget-swarm.yaml` was produced by an **uncommitted scratchpad script** — a committed generator is a prerequisite for the stress fragment (precedent for committed generators: `scripts/gen-adventurer.mjs`, `scripts/gen-houses.mjs`).
- The map generator has **no repeat/count primitive** — mass placement is either N grid glyphs or a fragment. Fragments are copied verbatim and are *not* drift-gated (only `generated_from:` files are); the map that includes them is.
- The per-enemy hot path is `enemy_ai` (`games/vigil/src/movement.rs:85`): snapshot Vec → per body `flow_dir` (O(1)) + `spatial::k_nearest` + `move_and_slide` + `get_mut`. Known superlinear-ish term: `k_nearest` (`ludion-spatial/src/spatial.rs:299`) collects-then-**sorts** all candidates in the probe rectangle; at `CELL_SIZE = 16.0` and 5000 bodies in the budget arena, ~70 bodies/cell. `update_flow_field` is enemy-count-independent (radius-capped, `NAV_FLOW_RADIUS` 48) and will stop being the top cost.
- E6 baseline at 500 enemies (`games/vigil/budgets/pinned-rtx3090.toml`): frame total 1.77 ms; `update_flow_field` 0.715, `enemy_ai` 0.69.

## Phases

### S1 — Stress scene + single-threaded Amdahl baseline (build first; ships a number on its own)

Everything here is sequential-world work: a scene, a generator script, profile instrumentation, tests. No parallelism.

**Work items:**

1. **Committed fragment generator** — `scripts/gen-stress-swarm.mjs` (Node, like `gen-houses.mjs`), parameterized by enemy/bolt/pickup counts, emitting `games/vigil/scenes/stress-swarm.yaml`. Deterministic output (no `Math.random` without a seeded PRNG; stable ordering) with a header comment naming the generator and its parameters. Reuse `budget-swarm.yaml`'s conventions: invulnerable player (`Health: hp: 1e9`), stable census, real enemy archetypes from the docs roster spread across the roster (creature models included — the demo should look like the game).
2. **Stress map** — `games/vigil/scenes/stress-horde.map.yaml`: same fabric as `budget-horde.map.yaml` (33×36 @ cell 4 = 132×144, solid perimeter, open interior, `env-night.yaml` + the swarm fragment), `ludion generate-map` → committed `stress-horde.yaml` under the existing map-drift gate. Start at **5000 enemies / 1000 bolts / 500 pickups**; the generator parameter is the scaling knob — raise until the exit criterion is met. Density note: 5000 in this arena ≈ one body per 2 u² — a packed horde wall, which *is* the separation workload, not an artifact. If `k_nearest` alone exceeds ~90 % of the tick, tuning `CELL_SIZE` (or a k_nearest partial-select instead of full sort) is a legitimate *sequential* fix to land first — it helps the real game and keeps the baseline honest — but no other pre-optimization before the baseline is recorded.
3. **Amdahl instrumentation** in `crates/ludion-engine/src/profile.rs` (the sanctioned wall-clock site): extend `profile_sim` to also time, per measured frame, (a) `WorldHash::compute`, (b) `extract_render_scene`, (c) command drain (`Engine::execute` of the tick's `SimStep`). Report them in a new `sequential` section of `SimProfile` (median each, same shape as `SystemTiming`); add `Deserialize` to `ProfileReport` so tooling can round-trip reports. Guard with the existing `observer_does_not_change_world_hash`-style test: instrumented and uninstrumented runs hash-identically.
4. **Baseline run** — `cargo run --release -p vigil -- --scene scenes/stress-horde.yaml --profile 120 --json budgets/stress-baseline-rtx3090.json` on the reference box (and the M4 twin when convenient). Commit the JSON. Compute and record the **Amdahl split** in this plan's S1-results note: parallelizable share = Σ(per-entity system medians) / (frame_total + sequential section), reported twice — the *game-loop* composition (drain + schedule + extract, no hash) and the *oracle* composition (per-tick hash included), because the demo claim rides the first and the CI gate cost rides the second.
5. **Stability + determinism test** — a `session.rs`-style double-drive over the stress scene (pattern: `budget_horde_is_deterministic_and_does_not_decay`, `games/vigil/tests/session.rs:377`): two runs of N ticks produce identical `WorldHash` traces and the census does not decay. Keep N small enough for the ~2-minute check.mjs budget; the long profiled run is the CLI invocation, not the test.
6. **Committed replay** — record `games/vigil/stress.lrp` (SimStep-only session over the stress scene via `engine.set_recording`, the `tests/replay.rs` pattern) with a replay test asserting the committed trace, re-blessable via `LUDION_BLESS=1`. This is the future oracle centerpiece.

**Exit criteria:**
- Sim tick median **> 8 ms** single-threaded on the reference Windows box at some committed generator parameterization (record which).
- Baseline JSON + Amdahl split committed; headline numbers recorded in the private determinism notebook.
- Stress scene under the map-drift gate; stability test and replay test green in the default check.mjs run.
- **Decision gate:** per-entity systems must be **≥ 60 % of the game-loop tick composition**. Below that, parallelizing systems can at best ~2.5× the tick — stop and rethink (candidates: attack the sequential terms first, or accept a more modest demo claim) before any J1 spend. Learning this costs days here vs. after a multi-k-LOC migration.

**S1 results (2026-07-31, reference Windows box, RTX 3090; `games/vigil/budgets/stress-baseline-rtx3090.json`):**

Parameterization: the generator defaults — **5000 enemies / 1000 bolts / 500 pickups** (no knob-raising needed). 120 measured frames after 30 warmup.

- Sim tick median **26.84 ms** — exit criterion (> 8 ms) passed 3× over.
- Per-entity system sum **25.68 ms**: `enemy_ai` 18.48, `move_projectiles` 6.18, `spatial_rebuild` 0.65, `cull_enemies` 0.33, `animate_pickups` 0.05 (remaining per-entity terms < 0.01 each). `k_nearest` did not pathologically dominate — no sequential pre-fix needed.
- Sequential section: `world_hash` **37.95 ms**, `extract` 2.71 ms, `command_drain` 0.002 ms.
- **Game-loop composition** (tick + extract + drain = 29.55 ms): per-entity share **86.9 %** — the ≥ 60 % decision gate passes; ideal 8-thread Amdahl on this split ≈ **4.2× on the loop** (≈ 7.6× on the heavy systems alone). J1 is worth building.
- **Oracle composition** (+ per-tick hash = 67.51 ms): per-entity share **38.0 %**. Finding: **`WorldHash` costs more than the entire sim tick** at this scale — the verification oracle, not the sim, dominates the CI gate's runtime. J0 must account for this (hash cadence in the gate, or hashing joins the parallelization agenda later); the demo claim rides the game-loop number, as planned.
- M4 twin baseline: **DONE 2026-08-01** — `games/vigil/budgets/stress-spatial-apple-m4-{1,2,8}t.json` committed.

**Addendum (2026-07-31, same day): `WorldHash::compute` optimized 2.65×** — 38.43 → **14.50 ms** at stress scale, byte-identical stream (no re-bless; committed replays are the proof). Streaming canonical `Serializer` (no `serde_json::Value` materialization, via `erased-serde`) + one ascending presence cursor per registered component instead of O(entities × registered types) probes. The oracle composition improves to per-entity ≈ 58 % (25.68 / 44.05 ms); the game-loop split above is unaffected (hashing was never in it). Repo-wide side effect: the two slowest tests halved (~66 → ~33 s), test lane 136 → 84 s. Remaining measured headroom (float formatting ~4.4 ms, erased dispatch ~3.8 ms, second storage lookup ~2.0 ms) deliberately not taken — each trades a boundary or clarity for ms the gate design (hash cadence) makes unnecessary.

### S2 — Groundwork (the former do-early items, now prerequisites)

**S2a — Derived RNG streams.**
- API in `ludion-core::rng`, copying the `variant_pick` splitmix64 shape: `DeterministicRng::derived(world_seed: u64, frame: FrameIndex, entity: EntityId) -> DeterministicRng` — splitmix-fold `(frame, entity.index, entity.generation)` into a stream id **masked to 63 bits** (the `<< 1` in `new_with_stream` discards the top bit), then `new_with_stream(world_seed, stream)`. A chunk-scoped variant taking a plain `u64` salt covers non-entity draws. Golden-sequence tests like the existing PCG vectors.
- The world seed must be reachable by systems: insert a `WorldSeed(u64)` resource alongside the RNG (`crates/ludion-sim/src/driver.rs:99`, mirrored in `ludion-engine`'s builder and snapshot). The master `DeterministicRng` resource stays — sequential draws remain legitimate where order is inherently serial.
- **Migration: the five vigil sites.** `spawner.rs` (4 sites → one derived stream per wave or per spawn slot, keyed on frame + slot index) and `progression.rs:184` (offer shuffle → derived from frame + player entity). This changes the draw sequence ⇒ **one `run.lrp` re-record + golden re-bless**, batched with any other hash-moving change in flight (the established `LUDION_BLESS=1` procedure).
- Amend `engine-architecture.md:203` ("One RNG"): one *seed*, one master resource, plus derived streams via the one sanctioned constructor — never ad-hoc seeding.
- Convention doc: a short section in the `determinism` docs topic — *when* to derive (any draw that parallel chunks might make, any draw whose order shouldn't couple distant systems) vs. when the master resource is fine.

**S2b — Declared-access completeness (the J1/J2 door).**
- Typed queries need no migration — they're already the idiom. The gap is per-entity `get`/`get_mut`/`insert`/`remove` being invisible to the query-drift verifier. Extend the world-side recorder (`world.rs:418-437`, which already attributes queries to the running system via `set_recording_system`) to also record per-entity component accessors, folding them into the observed shapes the drift gate checks (`L1126`/`L1127` in each game's `tests/replay.rs`).
- Exit: every vigil system's full component read/write set is observable from the drift gate. That observable access set is precisely what J1 chunking (and a hypothetical J2 scheduler) consumes. Expect a one-time widening of vigil's declared shapes.
- Explicitly *not* in scope: banning `get_mut` (the `&mut self` borrow model requires it mid-loop; a clippy `disallowed-methods` entry would fight the idiom, and the recorder catches what the lint can't see anyway).

**S2 results (2026-07-31, Lore revs 429–431):** S2a as spec'd — `derived`/`derived_salted` (splitmix64 fold, 63-bit mask, golden-vector-pinned), `WorldSeed` on all four world-construction paths with zero serialized-format change (restore reads the snapshot's existing `seed` field), both docs amended; vigil's five sites migrated (spawner: one `derived_salted` stream per spawn slot; progression: `derived` keyed on the `RunState` entity — it owns the offers and is non-optional where the player is not). The batched re-record touched only `run.lrp`; `stress.lrp` stayed byte-identical (the spawner's budget early-out precedes every draw) and image goldens didn't move. S2b as spec'd plus one necessary addition: the `Schedule` now **clears attribution after its last system** (`World::clear_recording_system`) — without it every host-side access (extract, hash, scene load) was attributed to the last-registered system. Recorder carve-out: a `RefCell` confined to the opt-in recording state is the world's only interior mutability; a miss records like a hit (intent semantics); `has` records nothing. Vigil's one-time widening: 31 systems. The widened gate immediately caught six genuinely new shapes when the migration's draw sequence reached previously-unexercised branches. **Findings for J1/J2:** (a) `RunState` is read by 30 of 32 vigil systems, written by 4 — the dominant serialization point for any system-level scheduler; (b) replay `.lrp`s embed periodic world keyframes, so a sim-behavior change leaves stale mid-run seek targets even when the replay gate stays green — the re-record was for keyframe honesty, not the gate.

### J0 — Foundations and the oracle (small, ~1–2k LOC; spec'd after S1)

- Denylist change from "no rayon" to "rayon only via `ludion_core::par`" (strict-tier `clippy.toml`s + a permissive carve-out in the owning crate). This requires **amending two written rules, not just clippy entries**: `engine-architecture.md:208` rule 5 ("sim is single-threaded, no rayon in sim crates") and the ECS freeze list's "no parallel scheduler" line (`engine-architecture.md:183`) — amend deliberately, referencing this plan.
- The 1/2/8-thread hash-identity gate over the **named corpus** (`vigil/run.lrp`, `vigil/stress.lrp`, `breakout/run.lrp`). Gate placement: CI matrix / `--full` lane — it must not blow the ~2-minute local check.mjs budget.
- A divergence-bisect tool (which frame diverged → which system → run both ways, diff components) — build it here, not during the first incident. Standalone value today: it also answers the golden/replay-churn watch-item, single-threaded.

**J0 results (2026-07-31, Lore revs 433–434):** All four bullets shipped; the open decisions settled as follows.

- **`par` is std plus a private rayon-core pool** (Serious Isaac 0033, owner-approved 2026-11-11), because a persistent pool must run borrowed closures and `ludion-core` keeps `forbid(unsafe_code)`. `ludion_core::par` is ~600 LOC (`par_chunks` / `par_map_chunks` / `ordered_reduce`; the work queue is the `ChunksMut` iterator behind a mutex, caller thread is worker 0, helpers are tasks on the pool). Rayon types stay banned outside `par.rs`; the carve-outs are `par`'s pool and rapier's internal scheduler (Serious Isaac 0020; its pool is owned by `ludion-physics` and sized `par::threads()`), gated by thread identity and the features gate (`scripts/physics-features.mjs`). Thread count: process default (initially 1) + thread-local scoped `with_threads` override, so concurrent drives can hold different counts.
- **Chunk size is part of the determinism contract** (the plan's "decide once"): changing a call site's `chunk_size` is a hash-moving edit under the established re-bless procedure; thread count is bit-irrelevant, pinned by `to_bits`-exact tests at 1/2/8 threads against a sequential reference a guard test proves order-sensitive. The tree-reduce alternative bought machinery for a knob rarely turned.
- **Denylist went mechanical where it could:** `std::thread::spawn`/`scope` are `disallowed-methods` in the pure-sim crates (ecs, sim, spatial, scene, all four games; two reasoned test-orchestration allows in vigil); ludion-core is the owning-crate carve-out, host-side crates (engine, facade, cli, assets) keep their legitimate thread seams. Architecture rule 5, the ECS freeze list, §3's sim-thread bullet, and the determinism topic all amended.
- **The gate replays the corpus at three thread counts in the game's own test binary** — not the CLI, which links only the built-in registry and would gate nothing. `tests/thread_identity.rs` in vigil + breakout, all `#[ignore]`d; run by a new check.mjs `--full` tail step, a new `thread-identity` ci.yml job (both OS runners — the parallel path rides the cross-OS matrix from day one), and a TeamCity config section. ~24 s warm for all five tests on the reference box. **Hash cadence decision: per-frame kept** — the 2.65× `WorldHash` optimization made thinning unnecessary, and per-frame is what localizes a divergence to the exact frame. `committed_replays()` in ludion-protocol widened to `stress.lrp` (no ceiling change needed).
- **The bisect tool is two instruments over one world-diff core** (`ludion-engine/src/bisect.rs`): `verify_replay_keyframes` (re-drive a committed `.lrp`, compare live state against every embedded keyframe — alignment is record order, not frame number, because free-run recordings batch ticks; this answers the golden/replay-churn watch-item and runs over the corpus in the same gate) and `bisect_divergence` (two `RunConfig`s → first divergent frame from the traces → re-drive that frame under a per-system probe → name the system, diff the components). `Schedule::run_probed` is the ECS seam (observation-only, hash-neutrality tested; `ScheduleObserver` untouched). New `L3024`; `--replay-verify <FILE>` on every game binary. First contact with real data caught a real bug: serde_json (no `float_roundtrip`) parses floats 1 ULP off, so keyframe values normalize through their registered component types before diffing — raw-JSON comparison would have failed every committed `.lrp`.
- Deliberately not done here: keyframe-skipping replay decode + the `MAX_DECOMPRESSED_LEN` derivation revisit (still queued privately for when the corpus grows), and no `ludion` prelude re-export of `par` (no game call sites until J1; it rides J1's migration commit).

### J1 — Dense column storage + parallel-for over queries (the payoff, ~2–4k LOC + migration; spec'd from the S1 profile)

- Hot components move from BTreeMap to sorted dense `Vec` columns keyed by entity index. `split_at_mut` gives disjoint `&mut` chunks in safe Rust; zipped chunks across columns handle multi-component queries.
- `query.par_for_each(ctx, |...| ...)` for element-wise systems — migration targets chosen by the S1 profile, not by guess: the stress scene's measured hot systems move first (expected: `enemy_ai`, `spatial_rebuild`, projectile movement, fragment updates). Note `enemy_ai`'s mid-loop `&World` reads (spatial probes, nav) — the chunk model must expose shared-read access alongside disjoint writes.
- Per-chunk `CommandBuffer`s applied in chunk order — slots into the existing deferred-command design. (Not built; `CommandBuffer` was deleted 2026-09-26.)
- **Explicit unfreeze decision required**: collides with the ECS freeze list ("no parallelism", ~2–3k LOC budget). Note dense columns also speed up the *sequential* sim — legitimate on their own whenever BTree shows up in profiles.
- Exit: the demo deliverable above, plus cross-OS bit-exactness (the parallel driver rides the same Windows/macOS sim-hash CI gate as the sequential sim).

**J1 results (2026-07-31 → 2026-08-01, Lore revs 436–437, 441, 444):** four waves — dense columns + spatial parallel-safe entry points (436), `World::par_for_each`/`par_join_fold` over the region model (437, ECS freeze budget explicitly raised for this named plan), the vigil migration (441: `enemy_ai` + `move_projectiles` under `par_for_each`; separation went Jacobi — the one deliberate behavior change, one `run.lrp` re-record; `spatial::rebuild`'s parallel attempt honestly reverted at 0.40 → 0.85 ms negative scaling), and the performance close (444).

### J2 — System-level parallelism (large, invasive, maybe never)

- Requires declared component access per system → abandoning `fn(&mut World, &SystemCtx)` for typed system params (Bevy-style); touches every system in every game plus `ludion-sim`.
- Scheduler computes fixed conflict-free batches from declared access + registration order (disjoint-access systems commute → deterministic). S2b's recorded access sets are the input data.
- Return is Amdahl-capped: ~10–30 systems, many tiny or dependency-chained. **J1 captures most of the win at a fraction of the cost; J2 may never clear the bar.** The demonstration goal does not change this: J1's numbers carry the demo.

**J2 evaluation (2026-08-01, computed from the final J1 profile + the S2b declared-access shapes; recommendation: NO-GO).** The plan existed so this decision would be made from a written analysis — here it is.

- **The ceiling, computed not guessed.** The 32 vigil system medians at 8 threads sum to 5.751 ms, and the distribution is brutal: `enemy_ai` 2.874 + `move_projectiles` 1.414 carry 74.6 %; the smallest 22 systems total **0.027 ms**. Greedy conflict-free batching in registration order over the *declared* access shapes (the set a static scheduler must use — the S2b "RunState: 4 writers" figure is the exercised set; declared writers number 10, and `Transform` is written by 13 / read by ~20) yields **31 batches out of 32 systems** — exactly two legal merges, worth **0.0085 ms** combined. Even abandoning the registration-order guarantee, the zero-sum correction bites: the big two are already internally parallel at ~66 % core efficiency, so co-scheduling anything against them contends for the same 8 cores — true ceiling ≈ **0.09 ms (1.6 % of the tick)**, against 0.3–1.5 ms of *new* per-batch fan-out overhead from `par`'s per-call scoped threads. The expected net is negative.
- **Cost: XL, larger than J1.** ~120 `.system(` call sites across four games, engine tests, facade examples, and the CLI template; replacing `SystemFn` with a typed system-param trait family in a freeze-listed 527-line `schedule.rs`; every doc topic that names the system signature. **Risk is qualitatively worse than J1's:** `par_for_each`'s disjointness is proven by `split_at_mut` (a miss is a compile error), while J2 makes declared access load-bearing at runtime — an under-declared `get_mut` becomes a genuine data race the 1/2/8 gate can only probabilistically catch — and batch composition becomes a second hash-moving tunable derived from declarations. The typed-params signature is also the exact "macro-heavy DSL / deep generic chain" the pillars ban, with trait-resolution errors where the North Star demands rustc-grade ones.
**Verdict: NO-GO, ratified by the user 2026-08-02.** J2 is not built; J3 stays "don't"; the plan closes here. Alternatives (1) and (2) below are already reflected in the tree — (1) shipped 2026-08-01 as the spatial static/dynamic split, (2) stays queued privately.

- **What moves the numbers instead, ranked:** (1) the **spatial static/dynamic index split** from the J1 wave-4 investigation — S/M-sized, hash-neutral by proof, collapses the 4.29 ms the big two still cost at 8t (est. tick 5.74 → ~1.9 ms at 8t, 22.9 → ~3.7 at 1t; honest side effect: it shrinks the J1 demo *ratio* since the parallel win rides those two systems — ship it anyway, the recorded J1 numbers stand as measured); (2) **parallel/incremental `world_hash`** — engine-only, structurally the `par_join_fold` shape J1 already shipped, attacks the 12.9 ms term that is 62 % of the oracle loop; (3) close this plan — J3 stays "don't".

## Costs and risks

- **Amdahl is the real constraint, not determinism.** Command drain, hashing, extract, command-buffer application stay sequential. Heavy systems at 70 % of tick → ~2.8× on 8 cores, not 8×. Own this number in every presentation of the result; S1's decision gate quantifies it before any migration spend.
- **Benchmark-special risk.** The stress scene must stay made of real game systems with game-plausible density; any load added purely to flatter the speedup invalidates the demonstration. The one sanctioned deviation is scale (5000 authored enemies vs. the game's 500 cap), and it uses the same bypass the shipped E6 gate uses.
- **`k_nearest` density blow-up.** At horde density the sort-based k-nearest is the likely top cost. If it pathologically dominates, fix it sequentially *first* (cell-size tuning / partial select) so the baseline measures the game, not one algorithmic cliff.
- **Draw-sequence churn.** S2a's RNG migration re-records `run.lrp` and re-blesses goldens once; batch it with other hash-moving changes.
- **Cross-platform float drift compounds.** The parallel driver adds reduction order to the existing FMA/toolchain drift surface; the cross-OS sim-hash gate must cover the parallel path from J0 on.
- **Carried surface.** Until a game needs the throughput, the job system is demo-and-gate infrastructure. Acceptable cost under the re-based trigger; the gate keeps it honest and unbroken.
- Snapshot/replay formats are **unaffected** — parallelism changes how a tick computes, not what state exists.
