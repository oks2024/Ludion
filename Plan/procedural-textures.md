# Plan: Procedural textures — a text recipe that produces a PBR map set

> **Status:** Wave 0 (the spike) not started. Decided 2026-10-23. Waves 1+ are recorded with
> triggers and wait on the spike's verdict.

## Why

Ludion consumes five PBR maps per material (`Plan/textured-pbr.md`), but has no way to *make* them:
textures arrive only through `ludion import`. The reference game's Blender kits fill the gap with
node-based Cycles materials baked per object. A node graph is opaque to an agent: it cannot read,
diff or iterate on it. An LLM-first engine wants the texture to be text — a recipe the agent writes,
renders, looks at and corrects — with the maps generated from it.

The claim that such a recipe reaches "really good results" is empirical, so a spike gates the full
plan (the `Plan/cooked-assets.md` Wave 0 precedent).

## Settled decisions (2026-10-23)

1. **Spike first, then the full plan.** A minimal core plus reference materials and the user's
   verdict gate everything below Wave 0.
2. **Tileable materials first; mesh-aware (Painter-like) texturing is a later wave.**
3. **A declarative YAML recipe** (`kind: texture`, `*.texture.yaml`): named steps forming a DAG,
   parametrized sub-recipes. Data, not code — no Rust per texture, no expression language. This
   keeps Pillar 4 (text is the source of truth) and the "Rust is the only Turing-complete layer" rule.
4. **Style-neutral.** Realistic, stylized and hand-painted must all be reachable from the same
   engine. Specialized per-style generators are a fallback, never the goal.
5. **Two layers.** Style-agnostic Rust primitives, including the hard generators (tile sampler,
   flood fill, distance field, height → normal / AO / curvature); and macros as parametrized
   sub-recipe files in an engine stdlib that a game references or overrides. Style lives in data,
   never in the engine.
6. **CPU, f32, bit-exact across architectures** (`ludion_core::math` libm, `ludion_core::par`).
   Recipe → PNG is a pure function. Each resolution is separately bit-exact.
7. **One external-image input op**; the core library stays fully procedural.
8. **Outputs are exactly Ludion's five maps** (emissive only when the recipe authors it) plus a
   16-bit linear height map.
9. **Committed, write-only, drift-gated.** `ludion texture build --check` compares regenerated bytes
   to the committed PNGs (the `mesh apply` precedent). An op-library change shows as a reviewed
   diff of generated files, never a silent re-texturing.
10. **Tile units (0..1), never pixels; tileable by construction** (periodic generators, wrap-around
    filters), so a recipe is resolution-independent.
11. **Crate `ludion-texgen`, linked by `ludion-cli` only** (the `ludion-cook` precedent). No game
    binary or `ludion-engine` links it. A pipeline verb satisfies the parity gate; no wire command,
    no editor surface (`CLAUDE.md` Non-negotiables).
12. **Verbs: `ludion texture build | check | vendor`.** `build` writes the maps and a JSON report
    (`--json`); `check` validates without writing; `vendor` copies a stdlib recipe into the project
    to override it.
13. **The stdlib is embedded in the binary, referenced with the `std:` prefix.**
14. **Validators.** An engine PBR-plausibility set (albedo range, roughness/metal sanity, normal
    unit length, tiling seam, periodicity) plus optional project rules in TOML, in the shape of
    `image-stats --check`. The reference game's lab rules can move into it.
15. **Kit consumption, spike.** Blender samples the generated sets as images and the existing
    per-object bake still runs. No engine change.
16. **Spike feedback loop.** A Ludion-rendered preview (sphere, plane, rounded cube under the
    Environment and one key light), a per-map sheet, per-step thumbnails, a 2×2 tiling view,
    the numeric validators and the JSON report. Comparison against a reference image is deferred.
17. **Anti-tiling in the spike is measured, not solved:** the tiling view and a periodicity
    validator expose repetition; bake-time macro variation on the kit piece covers it if needed.
18. **Speed budget (~40-step recipe, feedback included):** ≤2 s at 512², ≤10 s at 1024²,
    ≤40 s at 2048². Measured indicatively on a non-pinned dev machine during the spike; the
    pinned-M4 measurement is owed (`Plan/owed.md`).
19. **Revisits `Plan/textured-pbr.md` decision 1 and its "no texture-authoring surface" fence.**
    A text recipe is diffable source with generated, drift-gated maps, which removes the fence's
    reason; both places carry an amendment line.

## Waves

### Wave 0 — the spike

- `ludion-texgen` core: recipe parse, DAG evaluation, f32 tile-unit image buffers, the hard
  generators, the `std:` stdlib.
- `ludion texture build | check | vendor`, with the drift `--check`, the validators and the JSON
  report.
- The feedback loop of decision 16.
- Three reference materials: **cobble, oak planks, painted/rusty iron**. One is also restyled —
  **cobble realistic vs hand-painted** — by changing only recipe data and stdlib parameters.
- A log of iterations-to-result per material and of every missing op. The full plan's op list
  comes from this log, not from guesswork.
- One real kit piece of the reference game, end to end, beside its node-material twin (a small
  kit hook maps a generated set at the texel-density scale → bake → import → in-game). Detail in
  a private plan.
- The user's verdict sitting, judging each material against the current node-material bake and a
  CC0 photoreal reference on one preview rig.

**Exit — the verdict rule:**
- **Go** if at least 2 of 3 materials are at least as good as their node-material bake *and* the
  restyle reads as a distinct style.
- **One of three:** one targeted follow-up wave driven by the missing-ops log, then judge again.
- **None:** park. The crate is deleted; nothing outside it depends on it.

### Later waves — deferred, with triggers

Recorded so the decision is made from analysis, not under pressure. None starts before a Go.

- **Seed variants** — one recipe, N seeded outputs. Trigger: the periodicity validator or the
  user's eye reports visible repetition on a kit piece.
- **Wang-set output mode** — a tile set that removes repetition by construction. Trigger: seed
  variants do not fix repetition.
- **Wave B: runtime layering** — a shared tileable set plus a per-object detail layer on UV1 in
  the renderer, stochastic (hex) tiling and a world-space macro layer. Trigger: the spike's Go
  *and* a measured bake-time or memory cost of per-object baking that matters.
- **Mesh-aware (Painter-like) wave** — edge wear, curvature and AO-driven masks on a specific
  mesh. Trigger: tileable sets proven, and content that needs per-mesh wear.
- **Reference comparison in the feedback loop** — scoring a render against a reference image.
  Trigger: the log shows the agent iterating blind on a look.

## Out of scope

Node-graph UI, an editor texture surface, wire commands, an expression language, voxel texturing,
and any runtime procedural generation in a game binary.

## Risks

- **The claim fails.** Mitigated by the spike and its park rule; the crate is isolated.
- **Op-library churn re-textures committed art.** Mitigated by decision 9: a drift diff is a
  reviewed change.
- **Cross-arch float drift.** Mitigated by decision 6 and a cross-arch check on the pinned machines.
- **Visible tiling.** Decision 17 measures it; Later waves answer it.
