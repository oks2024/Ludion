# Audit: audio (2026-10-03)

**Scope.** Report only, at rev `42c38d98`. Files read: `crates/ludion-audio/src/lib.rs` (the sink, the mixer, the decode cache, the soft limiter) and `src/music.rs` (streamed Ogg Vorbis); `crates/ludion-engine/src/audio.rs` (the `AudioQueue`, the falloff rule, the log entry); the audio paths in `crates/ludion-engine/src/engine.rs` (`drain_audio`, `emit_audio`, `sync_audio_emitters`, `install_audio_queue`, `audio_listener`, `AUDIO_LOG_CAPACITY`); `AudioEmitter` in `components.rs`; `crates/ludion-core/src/audio.rs` and the L5xxx codes; `ludion_assets::decode_wav`; the host wiring in `crates/ludion/src/host.rs` (`wire_audio`) and `embed.rs`; vigil's emitters, sound constants and `games/vigil/tests/audio.rs`; `games/hello-paddle/tests/audio.rs`; `docs/audio.md`, `dev-docs/ludion-audio.md`, `Plan/phase-8-assets-and-sound.md` and `Plan/audio-ambience.md`. One throwaway probe ran outside the repo (lewton 0.10.2 decoding the crate's own `testdata/tone-stereo-44k.ogg`) and was deleted afterwards. Findings already in `Plan/code-audit-2026-07-25.md` are not repeated. B6 from that audit (anti-clipping was left to each call site) is resolved: `collapse_simultaneous` and `soft_limit` now live in the sink.

## Overall assessment

The boundary is right. Audio is plain data on a one-way channel. No lock is shared between the sim and the device callback. Nothing the sink does can reach a tick. The frame-stamped `audio_log` is a pure function of the sim, which makes it a good text-first test surface. A missing device degrades to a silent drain that never blocks. The WAV decoder is bounds-safe, and the music path is careful about not allocating in the callback. The weak spots sit around this core. The Vorbis loop seam includes the encoder's padding, so it is not gapless, and the test that claims it is passes anyway. The sink's message routing runs on no test machine. On a headless run, a broken sound reference produces no signal at all, and that is the agent's normal mode. Nothing caps polyphony. The remaining findings are quality and waste issues in the resampler, the per-tick emitter traffic, hard cuts and stale docs.

## Medium

### U1 — The music loop seam is not gapless: lewton's tail padding is played at every wrap · Medium · [verified]
**Evidence:** `crates/ludion-audio/src/music.rs:84-99` (`next_packet` passes through every decoded sample) and `:294-306` (end of stream leads straight to `reopen`). Nothing reads the last page's granule position. Probe: decoding `crates/ludion-audio/testdata/tone-stereo-44k.ogg` with lewton 0.10.2 gives **22080 frames, but the last page's `absgp` is 22050**. The 30 extra frames are encoder padding, which a conforming decoder trims.
**Why it matters:** `docs/audio.md` §Music and the module doc promise a gapless seam. Each wrap actually inserts the padding: here 30 frames (0.7 ms), and up to one long block (about 46 ms) in general. That is a click or dip on any authored seamless loop, which is exactly what music for the shmup will be.
**Gate false-green:** `a_looping_feed_runs_past_the_track_without_a_gap` (`music.rs:577-594`) measures the period as `one_pass.len() + 2`, where `one_pass` itself contains the padding. It shows that the decode repeats, not that the seam is clean. `it_decodes_a_stereo_track_at_its_native_rate` tolerates ±2048 frames, which hides the excess.
**Fix:** Track `get_last_absgp()` and truncate the final packet so total output equals the granule end. Then assert that the looping feed's period equals `absgp` exactly.

### U2 — The sink's message routing has no test coverage on any machine · Medium · [verified]
**Evidence:** `crates/ludion-audio/src/lib.rs:312-397`, the `run` loop. It resolves one-shots and loop syncs, sends `StopAllLoops` to both the feed and the callback, handles `MusicPlay`/`MusicStop`, refills on a timer and checks the dead-stream latch. That code is reachable only after `open_output()` succeeds. On CI, which has no device, every session takes `drain_silently`. On a developer box the two sink tests (`:1300-1332`) send no messages. `stopping_all_loops_clears_the_table` (`:1033-1059`) calls `HashMap::clear` directly. It never exercises the callback's `StopAllLoops` arm (`:517-520`), which also stops the music.
**Why it matters:** The part of the crate that decides what is heard has never been exercised. A routing regression would pass every gate, such as `StopAllLoops` no longer stopping the music or a `MusicPlay` failure skipping the refill.
**Fix:** Split the per-message match into a pure `route(message, &mut cache, &mut feed) -> Option<VoiceCommand>`, and split the callback body into a device-free `Mixer::render(&mut [f32])`. Test the sequence (message → command → rendered samples) without cpal.

### U3 — A broken sound reference is invisible on a headless run · Medium · [verified]
**Evidence:** `lib.rs:239-246`: with no device, `run` goes straight to `drain_silently` (`:461-463`), so `resolve` and its `L1104` warning (`:436-441`) never run. The engine only logs paths and never checks them (`engine.rs:1281-1293`). `check-scene` does not look at `AudioEmitter.sound` (its validator checks only `range`, `components.rs:2959-2972`). Vigil's guard is a hand-kept list (`games/vigil/tests/audio.rs:194-219`). It already omits `CHANT_SOUND`, the one sound that reaches the game only through data (a scene's `cue.sound`), so data-authored sounds are never checked.
**Why it matters:** The agent works headless. Suppose a typo goes into a `play()` path, a game doc's `cue.sound`, or a scene's `AudioEmitter.sound`, or someone commits a 24-bit WAV. Every gate stays green, the agent sees nothing, and the first sign is a human hearing silence. That costs exactly the iterations the North Star counts.
**Fix:** Let the silent sink still `resolve` each distinct sound once (decode without a device) and print the same once-per-version `L1104`/`L1101` warning. Better still, add a testkit helper, for example `assert_logged_sounds_decode(&engine, root)`, that walks `audio_log()` and decodes every named sound. A game's existing replay test then catches data-authored references too.

### U4 — Polyphony is unbounded: a sound re-fired across callbacks stacks voices without a cap · Medium · [verified]
**Evidence:** `lib.rs:502-526`. `voices: Vec<Voice>` grows by every one-shot that arrives. `collapse_simultaneous` (`:589-606`) merges duplicates only within one callback, about 10–21 ms (its own doc says so). Nothing limits voices per sound or in total, and nothing steals voices.
**Failure scenario:** A shmup fires a 0.3 s shot sound every 3 ticks. Each shot lands in a different callback, so roughly 6 copies of one sample sum at staggered offsets, and more with several guns. The sum runs deep into `soft_limit`'s knee: a loud, saturated wash rather than a hit. Each new high-water mark also grows `arriving`/`voices` inside the real-time callback.
**Fix:** Cap concurrent voices per sound (for example 4) and in total (for example 32), and steal the oldest voice with a short fade. Reserve both `Vec`s at stream build so the callback never grows them.

## Low

### U5 — Sound effects resample nearest-neighbour, while a linear resampler sits unused one file over · Low · [verified]
**Evidence:** `lib.rs:638-669` (`to_device_buffer`: downmix to mono, then pick the nearest sample) versus `music.rs:107-154` (`Converter`, a stateful linear interpolator). All 19 vigil WAVs are 44.1 kHz mono, and the usual Windows shared-mode device rate is 48 kHz. On such a device every vigil sound repeats roughly one sample in eleven, which adds aliasing and jitter distortion to tonal content: the chant, hound and level-up sounds. Audibility was not measured by listening.
**Fix:** Run SFX through `Converter` (one resampler, not two), and keep stereo SFX stereo the way music already is.

### U6 — Every emitter resends an unchanged `LoopSync` every tick, and each one costs a `stat` on the sink thread · Low · [verified]
**Evidence:** `engine.rs:1310-1360` emits one `LoopSync` per audible emitter per tick, whether or not the gain changed. It also clones each `AudioEmitter` (and its `String`) into a fresh `Vec`. `lib.rs:430` calls `stamp_of` (a filesystem metadata call) before the cache lookup, so every message costs a syscall. For manual loops, the `LoopId::Sound(String)` arrives in the callback and is freed there (`sync_loop`, `:566-576`), which means a heap free on the real-time thread every tick. In `audio_log` (capacity 4096, `engine.rs:406-412`), three audible emitters fill the whole log in about 23 s, pushing out the one-shots a long test may want to assert on.
**Fix:** Keep the last sent gain beside `audible_emitters` and send only on change (with an epsilon). Check stamps on a timer or watcher event rather than on every message.

### U7 — Stops and gain changes are hard cuts, so they click · Low · [verified]
**Evidence:** `LoopStop` and `StopAllLoops` remove the voice in the middle of a waveform (`lib.rs:514-520`). `sync_loop` applies a new gain in the next sample (`:568-571`). No ramp exists outside music.
**Failure scenario:** The player kills an enemy at point-blank range. Its presence loop is cut mid-cycle. A district switch cuts every bed at once.
**Fix:** Retire stopped loops through a 5–10 ms fade, and slew loop gain toward its target over about one callback.

### U8 — The tail of a play-once music track can be stranded until the next message · Low · [verified]
**Evidence:** `music.rs:210-212`: `is_feeding()` is `current.is_some()`. At the end of a track, `stage` clears `current` (`:295-300`) while `staging` can still hold more than one chunk. `refill` then returns as soon as the ring is full (`:326-327`), and the ring is normally full. With `is_feeding` false, the sink blocks in `events.recv()` (`lib.rs:320-325`). The last few chunks (tens of ms) play only when some later message arrives. If that message is a `MusicPlay` for a different track, `play` clears `staging` (`:258`) and they never play. Games that send messages every tick hide this. A quiet menu playing a sting does not.
**Fix:** Make `is_feeding` `current.is_some() || !staging.is_empty()`.

### U9 — Stereo music on a mono output device plays only the left channel · Low · [verified]
**Evidence:** `music.rs:146`: `out.push(if ich == 2 && c < 2 { lerp(c) } else { mean })`. With `out_channels == 1`, `c == 0` takes `lerp(0)`, the left channel, rather than `mean`.
**Fix:** Use the per-channel path only when `out_channels >= 2`.

### U10 — A music file rewritten in place is reopened at the next seam with the old converter · Low · [verified]
**Evidence:** `music.rs:101-104` (`reopen` replaces only the `Track`) and `:294-297`. `Current.converter` keeps the old rate and channel count. Re-exporting a looping track at another rate (pitch shift) or as mono (stereo deinterleaving of mono data: garbled, double speed) is heard at the next wrap under a running host, with no warning.
**Fix:** On reopen, compare rate and channels and rebuild the `Converter` if they changed. Keeping its phase only matters when they are equal.

### U11 — Losing the device is permanent for the session; a stream that stalls without erroring backs up an unbounded queue · Low · [verified / suspected]
**Evidence:** [verified] The `dead` latch (`lib.rs:259`, `:328-330`, `:532-538`) never clears, and nothing reopens the device or follows a default-device change. Unplugging headphones silences the rest of a shipped game's run (`L5002` help: "restart the host"). That is documented, but it is a poor answer for players and for the iOS target's route changes. [suspected] Both channels are unbounded (`host.rs:243`, `lib.rs:254`). If a backend stops calling back without raising an error (an OS audio interruption), the sink keeps queueing `VoiceCommand`s. On resume the callback applies the whole backlog at once: a burst of stale one-shots, with `arriving` growing in the real-time thread. No reproduction was attempted.
**Fix:** On `L5002`, try to reopen the default device with backoff. Bound the command channel, or drop one-shots older than about 100 ms using a timestamp the sink thread sets.

### U12 — A 16-bit PCM `WAVE_FORMAT_EXTENSIBLE` file is rejected with a misleading message · Low · [verified]
**Evidence:** `crates/ludion-assets/src/lib.rs:462-467` accepts only `audio_format == 1`. An extensible header (`0xFFFE`) whose subformat is PCM produces "audio format 65534 is not uncompressed PCM (format 1)", although the samples are uncompressed PCM. The help text ("re-export as 16-bit PCM") does not say what to change.
**Fix:** Accept `0xFFFE` when `cbSize >= 22` and the subformat GUID is PCM, or name `WAVE_FORMAT_EXTENSIBLE` and the export setting in the message.

### U13 — Stale docs: two places still say "the mixer has no limiter", and the sink's dev-doc predates music and the facade wiring · Low · [verified]
**Evidence:**
- `crates/ludion-engine/src/components.rs:2917-2918`: `AudioEmitter.gain` says "The mixer has no limiter, so leave headroom". This field doc becomes the schema description the editor shows.
- `games/vigil/CLAUDE.md:103`: "the mixer has no limiter". `soft_limit` exists (`lib.rs:552-560`).
- `dev-docs/ludion-audio.md:12`: says `ludion-cli`'s hosts call `set_audio_sender`/`spawn`; it is the facade's `wire_audio` (`crates/ludion/src/host.rs:241`).
- `dev-docs/ludion-audio.md:62`: says `CategoryGains { sfx, ambient }`; there is now a `music` field.
- `dev-docs/ludion-audio.md:86`: shows a three-argument `spawn`; it now also takes `seconds_per_tick`.
- `dev-docs/ludion-audio.md:109`: "blocks on `events.recv()`"; it uses `recv_timeout` while music feeds.
- `dev-docs/ludion-audio.md:111`: says the cache is `HashMap<String, Arc<Vec<f32>>>`; it is now `HashMap<String, Decoded>`, stamped and caching failures.

**Fix:** Correct these lines. Say "soft-limited above 0.8; headroom keeps dynamics" where the docs currently say "no limiter".

## Checked and healthy

- **Determinism boundary.** `AudioQueue` is a resource outside the hash and snapshots. Presentation systems may write it, but they run once per tick, not once per render frame. `audible_emitters` and the `CategoryGains` are host-side only. The sink has no path back into the world. Emitters and `play_at` resolve the listener with `hierarchy::world_transform`, so parented emitters and cameras are placed correctly. Emitters are visited in ascending `EntityId`, and stops are sent before syncs (`engine.rs:1310-1360`).
- **Threading.** No mutex is shared between the sim and the callback. The callback only uses `try_recv` on crossbeam channels. The `IDLE` pool lock is taken only at spawn and session end. The pooled-thread workaround for cpal 0.15's WASAPI COM-apartment cache is documented and tested.
- **Headless behaviour.** No device means one `L5001`, then a drain that never blocks. `AudioSink::drop` waits only for the engine sender to drop, and `embed.rs:707-710` orders the bindings so that wait cannot hang.
- **WAV decoder bounds.** Chunk sizes go through `checked_add` and are checked against the file length. Odd chunk sizes get their pad byte. A truncated header, a missing `fmt `/`data` chunk, a non-whole frame count, 8-, 24- and 32-bit samples, float or compressed data, more than 2 channels and rates below 8 kHz all return a readable `L1104`. A zero-length `data` chunk decodes to an empty clip that plays nothing; the `advance_into` guard prevents a spinning loop.
- **Callback safety.** Indexing in `advance_into` and `MusicPlayer::mix_into` is guarded: chunk lengths are whole frames, including `stop_after`. `MusicChunk` is a fixed array, so music allocates nothing in the callback. Generations discard stale chunks and keep newer ones until their command arrives.
- **Restore and switch semantics.** Every world rebuild sends `StopAllLoops`, which also stops music. Emitters resync on the next tick from a cleared liveness set. Manual loops and music are documented as the game's to resend. `audio_log` is bounded, so it does not leak.
- **Error codes.** L1104, L1136 and L5001–L5003 are registered, explained, and listed in `DECLARED_CODES`.
- **Licences.** cpal (Apache-2.0), lewton (MIT/Apache-2.0) and crossbeam are permissive. lewton's `ogg` dependency is BSD-3-Clause, the same as several crates already in the tree (`bindgen`, `tiny-skia`). It is not a new kind of obligation.
- **Soft limiter caveat (not a defect).** `soft_limit` is a static waveshaper, not a gain-riding limiter. Peaks above 0.8 gain mild harmonics instead of flat-topping. That is the right trade for the cost, but the docs' "inaudible" wording oversells it.

## Suggested order of work

1. **U2.** Factor `route`/`render` out of `run` and the callback, and add device-free tests. Every later fix then has a gate.
2. **U1.** Granule-accurate end trimming, plus an exact-period seam test. Music shipped today and the shmup will loop it.
3. **U3.** Headless sound-reference checking: silent-sink resolve and/or a testkit helper wired into vigil's replay test.
4. **U4 and U7 together.** Voice caps with fade-stealing and short stop/gain ramps, which share one per-voice envelope.
5. **U5, U6, U8, U9, U10.** Small, local fixes in `lib.rs`/`music.rs`.
6. **U11, U12, U13.** Device reopen, extensible WAV support and doc corrections.
