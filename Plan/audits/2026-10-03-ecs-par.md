# Audit: the ECS core, the deterministic job system, and WorldHash (2026-10-03)

**Scope.** Report only; no fixes applied. Read at rev `aef0b9f2`: `crates/ludion-ecs/src/*`
(entity allocator, storage, query and par-query joins, registry, schedule, world, hierarchy cascade
entry points), `crates/ludion-core/src/{par,collections,rng,math,panic_capture}.rs` and
`math/rotation.rs`, `crates/ludion-sim/src/{driver,hash}.rs` and `hash/canonical.rs`, the denylist
generator `scripts/clippy-denylist.mjs` and the per-crate `clippy.toml` tiers, the canary
(`ci/scripts/denylist-canary.{sh,ps1}`, the `denylist-canary` and `thread-identity` jobs in
`.github/workflows/ci.yml`), `games/vigil/tests/thread_identity.rs`, vigil's live `par_for_each` sites
(`movement.rs` `enemy_ai`, `combat.rs`), glam 0.30.10's SSE2 and NEON `Quat`/`Vec4` sources, and the
docs `dev-docs/{determinism,sim-parallelism,ludion-ecs,ludion-core}.md`. One throwaway clippy probe
was run in a scratch crate outside the repo and then deleted (E3).

## Overall assessment

This is the most solid subsystem I have audited in this series. `par` gets every determinism
property it claims: chunk boundaries are static, per-chunk results come back in index order,
reductions are a left fold, the lowest-index panic wins, and the 1-thread path runs the same code.
The ECS region model lifts `&mut` columns out of the world and restores them before a panic resumes.
`ParCtx` exposes only `&World`, so a chunk cannot draw from the master RNG at all. The allocator,
storage and hash walk are oracle- and proptest-pinned, and `WorldHash` no longer goes through a
`serde_json` round trip. I found no live determinism defect. The weak spots are in the guards around
the code. The canonical CI canary is a weaker copy of the local one (E1). `dev-docs/determinism.md`
tells authors glam's `slerp` is cross-arch safe, which it is not (E2). The clippy lists have two
verified bypasses (E3). The hash cannot see a field changing between NaN, ±∞ and `None` (E4). Several
docs and one diagnostic's help text describe behaviour that has since changed (E5, E6).

## Medium

### E1 — CI's `denylist-canary` job is a weaker inline copy: it probes only `HashMap` and accepts any clippy failure as proof · Medium · [verified]

**Evidence.** `.github/workflows/ci.yml:371-384` appends only a `HashMap` use to
`crates/ludion-core/src/lib.rs`. It then treats *any* non-zero clippy exit as `denylist ok`. The real
canary is `ci/scripts/denylist-canary.sh:41-56` (and `.ps1:33-48`). It appends a `HashMap` **and** an
`x.sin()`, and it requires the output to name both `disallowed type` and `` `f32::sin` ``. Its header
(`.sh:2-3`, `.ps1:2`) says the CI job runs it, but no line of `ci.yml` invokes `ci/scripts/denylist-canary.*`.
Only `scripts/check.mjs --full` runs the strong version (`check.mjs:300-302`).
`dev-docs/determinism.md:103-105` describes the strong version as "the denylist-canary job".

**Why it matters.** CLAUDE.md names `ci.yml` as the canonical gate set. In CI the libm ban, which is
the rule behind cross-arch `WorldHash` identity, is never proven to fire. The "rejected for the right
reason" check that the local script adds was written because a bare failure proves nothing.

**Failure scenario.** An edit to `scripts/clippy-denylist.mjs` drops `math` from the `strict` tier
(for example, while splitting tiers). `--write` regenerates every file, so `lists-in-step` passes.
The tree has no violation, so clippy passes. The CI canary still sees the `HashMap` rejection and
prints `denylist ok`. Only someone who runs `check.mjs --full` on their own machine notices. Second
case: a toolchain or edition bump makes the appended snippet fail to compile for an unrelated reason.
CI passes the job without clippy linting anything.

**Fix.** Replace the job's three inline steps with `bash ci/scripts/denylist-canary.sh` (`pwsh` on
Windows), as `thread-identity` already reuses the shared selector. While there, add a third probe:
`std::thread::spawn` in a **sim-tier** crate (`ludion-ecs`). Today no gate shows that the thread ban
fires anywhere.

## Low

### E2 — `determinism.md` lists glam's `slerp` as libm-pure; on x86_64 it uses glam's own SSE2 sine polynomial, and `Quat`/`Vec4` dot products associate differently from NEON · Low · [verified]

**Evidence.** `dev-docs/determinism.md:59-61` says glam's trig "(`Quat::from_rotation_*`,
`from_euler`, `slerp`, …) is pure-Rust too" because the workspace enables glam's `libm` feature
(`Cargo.toml:76-77`). In glam 0.30.10, `src/f32/sse2/quat.rs:737-778` `slerp` computes its three
sines with `m128_sin`. That is glam's DirectXMath polynomial, not libm. It then divides by
`sin θ`. The NEON build (`src/f32/neon/quat.rs:762-767`) and the scalar build call `math::sin`
(libm `sinf`) and multiply by the reciprocal. Separately, `sse2.rs` `dot4_in_x` sums
`(x+z)+(y+w)`, while `neon.rs:41-45` uses `vaddvq_f32` (pairwise `(x+y)+(z+w)`). So
`Quat::dot/length/normalize` and `Vec4::dot/length` can differ in the last bits between the two pinned
platforms. The team knows this locally: `crates/ludion-core/src/math/rotation.rs:120-121` and
`ragdoll.rs:149-151` hand-normalize for exactly this reason. The rule doc says the opposite, and
nothing enforces it mechanically. `Quat::mul_quat` and the `Vec3A` dot3 do match across the two
backends (checked).

**Why it matters.** No sim caller uses `slerp`, `Quat::normalize/length/dot` or `Vec4` today (grep of
`games/*/src`, `ludion-engine`, `-physics`, `-spatial`, `-sprite`, `-scene`, `-sim`). The first author
who believes rule 4, for example slerping a turret's aim, gets a Windows-recorded `.lrp` that drifts
on the M4. Cross-OS identity is "a signal, not a gate", so the drift would surface late, as an
unexplained replay mismatch.

**Fix.** Correct the doc. Add sim-tier `disallowed-methods` entries in `clippy-denylist.mjs` for
`glam::Quat::{slerp, normalize, length, length_recip, dot}` and `glam::Vec4::{dot, length,
normalize}`, each with a reason that points at `ludion_core::math` hand-rolled equivalents. Before
relying on these entries, check that clippy resolves the re-exported paths.

### E3 — two clippy-list bypasses: `thread::Builder::spawn` and `SystemTime::elapsed` · Low · [verified]

**Evidence.** The `threads` group bans only `std::thread::spawn` and `std::thread::scope`. The
`clock` group bans only `Instant::now` and `SystemTime::now` (`scripts/clippy-denylist.mjs:52-65`).
A scratch crate with those four entries in its `clippy.toml` flagged the control
`std::thread::spawn`. It did **not** flag `std::thread::Builder::new().spawn(..)`, or
`std::time::UNIX_EPOCH.elapsed()`, which reads the wall clock without calling `now` at the call
site. `Instant::elapsed` and `Builder::spawn_scoped` have the same shape. No sim crate uses any of
these today.

**Why it matters.** These are the exact things rules 2 and 5 forbid, and the doc presents the lists as
the enforcement. A wall-clock read inside a system makes replays non-reproducible in a way that only a
cross-run diff reveals.

**Fix.** Add `std::thread::Builder::spawn`, `std::thread::Builder::spawn_scoped`,
`std::time::SystemTime::elapsed` and `std::time::Instant::elapsed` to the generator's groups.

### E4 — `WorldHash` encodes NaN, +∞, −∞ and `None`/unit all as `n`, so a divergence between those states is invisible · Low · [verified]

**Evidence.** `crates/ludion-sim/src/hash/canonical.rs:24-27` and `:314` map a non-finite float, a
`None`, a unit and a unit struct to `null`. The tests pin this:
`hash.rs:478-494` asserts `digest(&f32::NAN) == value_digest(&Value::Null)`. So a field that is
`Some(NaN)` in one run and `None` in the other hashes identically, and so does a NaN in one run and
+∞ in the other. The rule is frozen in `ludion.worldhash.v1`.

**Why it matters.** A NaN in sim state is almost always the first visible symptom of a bug, and it
is exactly the moment the per-frame hash trace should report a difference. Two runs that diverge into
different non-finite values stay hash-identical until the bad value feeds back into finite data,
which can be many frames later or never, so bisection starts from the wrong frame.

**Fix.** Changing the byte stream is a v2 rule change that re-records the whole corpus, which is not
worth it alone. A cheaper fix: have `Canonical` count the non-finite floats it maps to `null`, and have
`WorldHash::compute` report a one-shot warning naming the component and entity. A NaN reaching the
sim is worth a diagnostic whatever the hash does. Keep the v2 encoding (`#nan`/`#inf`/`#-inf`) as a
note for the next deliberate hash bump.

### E5 — stale docs about the identity gate and the storage backend · Low · [verified]

- `games/vigil/tests/thread_identity.rs:4-6` says "No vigil system calls `par` yet … so this gate is
  trivially green today". `enemy_ai` (`movement.rs:171`) and `move_projectiles` (`combat.rs:21`) are
  both `par_for_each` regions now. `:153-154` ("today's single-threaded code") is stale for the same
  reason. A reader sizing the gate's value is told it tests nothing.
- `crates/ludion-core/src/collections.rs:13-16` and `dev-docs/ludion-core.md:46` say ECS storage is
  "built on `StableMap<u32, T>`". It has been dense `keys`/`values` columns plus a slot table for a
  while (`crates/ludion-ecs/src/storage.rs:1-24`). The *rule* those lines state still holds (the join
  needs ascending columns), so only the factual clause needs rewording. This was flagged before and
  is still present.
- `dev-docs/determinism.md:103-105` describes the strong canary as the CI job (see E1).

**Fix.** Reword each line. None of them is load-bearing code.

### E6 — `L4007`'s help says the sim is "paused at the failing frame" and that `sim.resume` "re-runs the same system against the same world"; neither is true · Low · [verified]

**Evidence.** `crates/ludion-sim/src/driver.rs:471-476`. `do_tick` advances the frame counter even
on a panicked tick (`:431-432`). The driver's own test confirms it: after a panic on frame 2,
`driver.frame()` is 3 (`:921-926`). Resuming runs frame 3 from the **first** system, with frame 3's
inputs. Systems registered before the panicking one run a second time on a world they already
mutated. A system that panics on a frame-dependent condition will not panic again.

**Why it matters.** Errors are the UX budget (Pillar 5). An agent following this help believes a
resume is a safe retry against the same state. It is actually a continuation from a world no clean
run can reach, at a different frame. `sim.hash` in that state reports a frame one past the one the
diagnostic names.

**Fix.** Rewrite the help: the sim paused after frame N's tick, with the systems after `<system>`
skipped. The world holds whatever the panic left. Resuming continues at frame N+1 from the first
system and does not retry. To retry, restore a snapshot or reload the scene.

## Checked and healthy

- **`par` (`crates/ludion-core/src/par.rs`).** Chunk boundaries come from `chunk_size` only. The work
  queue is a mutex-guarded `ChunksMut`, so which worker takes a chunk does not matter.
  `par_map_chunks` writes each result into a slot indexed by its chunk, and `ordered_reduce` is a
  plain left fold over those slots. No float association depends on the worker count. All chunks run
  before the lowest-index panic propagates, and its site travels with it (`put_site`). An effective
  count of 1 runs inline through the same function. `with_threads` is restored when it unwinds.
- **Region model (`par_query.rs`).** The join runs sequentially, using the same gallop merge as
  `query`. `&mut` columns are split by progressive `split_at_mut`, with no `unsafe`. Lifted boxes go
  back before `resume_unwind`, so `lifted` is cleared on every path. Inside a region, `get` for a
  lifted column is `L0026` and `has` panics; neither reports absence. `ParCtx::in_join` rejects stale
  handles. `par_join_fold` folds in chunk order. A chunk holds `&World` only, so it cannot reach
  `resource_mut::<DeterministicRng>()`. "No master-RNG draw inside a chunk" is therefore enforced by
  the types, not by convention.
- **The live par site.** vigil's `enemy_ai` closure writes only its own row and defers spawns until
  after the region. Its reads (`spatial::k_nearest_entries`, `move_and_slide_at`, `nav::flow_dir`) go
  through `&World`. No sim crate holds `Mutex`/`RefCell`/`Cell`/atomics outside the access recorder
  (grep), so nothing shared is mutated in completion order. The recorder files reads into a set.
- **Identity gate wiring.** `replay_hashes_with` drives on the calling thread, so the per-thread
  `with_threads` override is the one in effect for that drive. `stress-horde.yaml` carries 5,000
  enemies plus a player and a `RunState`. That is about 157 chunks at `ENEMY_AI_CHUNK_ROWS = 32`, so
  the 2- and 8-thread drives really do fan out.
- **Allocator.** It is LIFO. The generation bumps on free, so a despawned handle fails before its slot
  is reused. `from_live` and `from_state` validate before mutating (`L0025`). `state_if_irreducible`
  keeps clean snapshots byte-identical. `despawn_many` gives the same free-list order as the loop.
  The generation wraps only after 2^32 frees of a single slot, which is out of reach in practice.
- **Storage.** It keeps ascending keys with an aligned slot table. Splices repair the slot table, and
  the randomized oracle test covers every method.
- **`WorldHash`.** It walks live sim entities in ascending slot order, with one presence cursor per
  registered component, in registration order. Presentation rows sit past every sim index, so they are
  never visited. The streaming `Canonical` encoder is pinned to the old `Value` walker by a corpus and
  by proptests over every `f32`/`f64` bit pattern and arbitrary JSON. The `serde_json` round-trip cost
  (code-audit 2026-07-25 C10) is fixed. Excluding resources and the free list is documented, and the
  resource half was already reported (C-audit B4).
- **Schedule.** Systems run in registration order and names are unique (`L4018`). The phase returns to
  `Host` before `SystemPanic` is written. The hook installs once and is gated per thread by a flag, and
  the flag reaches `par` workers. Presentation systems are scheduled after the sim and physics systems
  (`engine.rs:722-733`), so a cosmetic panic never skips sim work.
- **RNG.** The PCG32 reference vector matches. Derived streams fold through splitmix64 and are masked
  to 63 bits. `WorldSeed` is inserted on both `new` and `restore`.
- **glam.** The workspace enables the `libm` feature, which routes glam's scalar trig through libm.
  `Quat::mul_quat` and the `Vec3A` dot3 use the same operation order on SSE2 and NEON (see E2 for the
  exceptions).
- **`L0027`.** It sorts names before reporting, so `TypeId` order is never observable.
- **Denylist tiers.** `lists-in-step` fails on a crate with no tier, on a hand-edited list, and on a
  permissive file that carries lists.
