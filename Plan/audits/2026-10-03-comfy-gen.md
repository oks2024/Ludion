# Audit: the ComfyUI generation pipeline (2026-10-03)

**Scope.** This is a report-only audit at rev `47fb73a1`. It covers:

- **`crates/ludion-gen`.** `client.rs` (ureq + tungstenite against ComfyUI), `workflow.rs`
  (API-format parse, title overrides, seed injection, `/object_info` validation), `recipe.rs`,
  `run.rs` (upload → submit → follow → download → `run.json`), `sheet.rs`, `accept.rs`
  (provenance, image re-encode, mesh accept through `ludion-import`), `clock.rs`, and the mock
  server suite in `tests/mock.rs`.
- **The CLI verb.** `ludion gen` in `crates/ludion-cli/src/gen_cmd.rs` with its `--json`
  contract and `crates/ludion-cli/tests/gen.rs`.
- **The recipe and origin documents** in `crates/ludion-scene/src/generation.rs`. Read only where
  the gen path depends on them.
- **The editor side.** The Tauri host's `editor/app/src-tauri/src/generation.rs` and the
  Generation view.
- **Committed outputs.** vigil's workflows, recipes and accepted assets under
  `games/vigil/generation/` and `games/vigil/scenes/meshes/idol-generated/`.
- **Docs.** `docs/generation*.md` and `dev-docs/ludion-gen.md`.

The sheet's glyph table (`Plan/audits/2026-10-03-fonts-ui.md` F3) and the Generation view's
stale-result race (`Plan/audits/2026-10-03-editor-parity.md` X7) are already reported and not
repeated here.

## Overall assessment

The crate is carefully built:

- Server-supplied filenames never reach the filesystem.
- Prompts reach the graph through `serde_json`, so they are escaped correctly.
- The address is kept out of every artifact.
- Every failure mode has its own code and recovery line.
- The mock is a real TCP/WebSocket server driving the real HTTP client.

The weak spots sit where the pipeline meets time and shared state:

- **Provenance drift.** An accepted asset's `prompt` and `inputs` are read from the recipe *as it
  is at accept time*, not as it was submitted.
- **A blind spot in the follow.** `gen run` submits before it subscribes to `/ws`, which ComfyUI
  does not replay.
- **All-or-nothing runs.** One failed job makes the whole run's other candidates unreachable.
- **Shared upload names.** Uploads overwrite each other by file name.

None of these touches the engine or a gate: an accepted asset is ordinary content, and regeneration
is never a gate. They erode exactly what the arc promises, though: a trustworthy record of origin
and a loop that closes without a human.

None.

## Medium

### C1 — An accepted asset's `prompt` and `inputs` come from the recipe at accept time, not from the run that produced it · Medium · [verified]

**Evidence.**
- `crates/ludion-gen/src/accept.rs:366-419` (`provenance`) re-resolves the recipe from disk:
  - `recipe::resolve(&recipe_path)` at `:373`.
  - It applies the *current* overrides to the *current* workflow at `:395`.
  - It writes `prompt: run::prompt_text(&graph)` and `inputs: resolved.doc.inputs.clone()` at
    `:417-418`.
- `workflow_hash`, `seed` and `checkpoints` in the same block come from `run.json`. One origin
  block therefore mixes two moments.
- `run.json` stores `recipe_hash` (`run.rs:124`). Nothing compares it at accept, and the origin
  block carries no recipe hash.
- The doc comment at `accept.rs:363-365` says the prompt and inputs "need the recipe re-resolved,
  because … neither survives in the report". That is a choice in `run.rs`, not a constraint.

**Why it matters.** Provenance is "a record of origin" (decision 13), and `prompt` is "the one field
a human actually reads a year later". The documented loop edits the recipe between runs:
`docs/generation-craft.md:110` says "bump the base seed per run", and Wave 1 step 7 says
"read → edit the recipe". So accepting from any run but the newest records a prompt that never
produced the asset.

**Failure scenario.**
1. Run 3 uses prompt A. The author edits to prompt B and starts run 4.
2. On reflection, the author accepts run 3's candidate #5.
3. The sidecar says `prompt: B`, `seed: <run 3's>`, and `workflow_hash: <run 3's>`.

The same happens in the editor: the run picker offers older runs, and Accept from them writes the
current prompt. If the recipe was renamed since the run, the accept is refused outright (`L1172`),
even though the candidate is on disk.

**Fix.** At `gen run`, write the resolved `prompt` and the `inputs` snapshot into `run.json`, using
the existing `#[serde(default)]` posture for old reports. Build `Origin` from the report alone. Add
`recipe_hash` to the origin block, or at least warn at accept when the recipe's current hash
differs from `run.json`'s.

### C2 — `gen run` submits every job before it opens `/ws`, so a job that finishes first is never observed and the run waits out its whole timeout · Medium · [suspected]

**Evidence.**
- `run.rs:246-249` submits all `count` graphs. `run.rs:272` writes `run.json`. Only then does
  `run.rs:278` call `client.follow`, which opens the socket (`client.rs:333`, `:341-353`).
- `follow_stream` (`client.rs:355-418`) only completes a job on an `execution_success` or
  `executing {node: null}` frame. It never checks `/history` for jobs that finished before it
  connected.
- The ComfyUI server sends per-client events only to a socket already registered under that
  `clientId` (`send_json` drops a message whose `sid` is not connected). On connect it sends
  `status` and the *currently* executing node, never completed prompts. This is the suspected
  half: that behavior is ComfyUI's, not exercised here.
- The mock hides this. `tests/mock.rs:299-365` replays the full frame sequence of every prompt
  submitted so far whenever a socket connects, and it ignores `clientId`.

**Why it matters.** A resubmitted identical graph is a full ComfyUI cache hit and completes in
milliseconds, before the socket opens. That happens whenever the recipe and seed are unchanged:

- The editor's **Generate** "runs the recipe as committed: no count or seed override rides in from
  the UI" (`docs/generation.md:58`). A second Generate without an edit resubmits the same graphs.
- An agent re-runs after a failed download.

**Failure scenario.**
1. Click Generate twice on `idol-portrait` (count 8, seed 300) without editing.
2. The second run's jobs finish, all cached, during the submit loop.
3. The view spins for 600 s and then shows `L1170`. Its recovery, `gen fetch`, is not offered in
   the editor (see C5).

**Fix.**
- Open the socket before the first `POST /prompt`. This is ComfyUI's own client pattern.
- After connecting, and on every read timeout slice, poll `/history` once for the still-pending
  ids.
- Make the mock drop frames for prompts that completed before the socket connected, so the gate
  pins the ordering.

### C3 — One failed job sinks the whole run: the other candidates keep running and can never be fetched or accepted · Medium · [verified]

**Evidence.**
- **The follow aborts.** On the first `execution_error` frame, `follow_stream` returns `Err`
  (`client.rs:393`); `follow_polling` does the same via `self.history(id)?` (`client.rs:432`).
  `run` propagates it (`run.rs:278-280`), leaving `run.json` at `status: "submitted"`. No
  `/interrupt` and no queue delete is sent for the remaining jobs.
- **`history()` turns a failed entry into an error.** It returns `Err(L1169)` for any history
  entry with an `execution_error` message or `status_str: "error"` (`client.rs:272-274`,
  `:592-618`).
- **Status and fetch inherit it.** `status` (`run.rs:294-302`), `fetch` (`run.rs:323-331`) and
  `download` (`run.rs:436`) all call `client.history(id).map_err(one)?`. The failed job's entry
  therefore aborts each of them before any other job is looked at.
- **Accept is blocked.** It requires `status: "ok"` (`accept.rs:331-343`).

**Why it matters.** A per-seed out-of-memory error or a node failing on one input is ordinary at
`--count 8`. The GPU still spends minutes on the other seven jobs, the author cannot see or keep
any of them, and `gen status` cannot even report which job failed.

**Failure scenario.** `gen run idol-portrait --count 8`, and job 3 hits a CUDA out-of-memory error:

- `gen run` exits `L1169`.
- `gen fetch` exits `L1169` on job 3 every time.
- `gen sheet` and `gen accept` refuse the `submitted` run.
- Jobs 4–7 run to completion on the server anyway.

**Fix.**
- Treat a failed job as one outcome among N. Record it per job in `run.json` (for example, a
  `failed` list with node, class and message), download the rest, and finalize with a status such
  as `partial` that `sheet` and `accept` honor.
- `status` should report failed jobs rather than error out.
- On an abort, optionally `POST /queue {"delete": [...]}` for jobs not yet started.

### C4 — Uploads are filed under the local file name with `overwrite: true`, so two different source images with the same name replace each other on the server · Medium · [suspected]

**Evidence.**
- `client.rs:195-201` names the upload after `path.file_name()`.
- `client.rs:541-542` sends `type=input`, `overwrite=true`.
- The returned server name is what `LoadImage` holds (`run.rs:214-217`). `LoadImage` reads the
  file when the job *executes*, not when it is submitted.
- `graph_hash`, and with it the run id's hash half (`run.rs:218-220`), covers the uploaded *name*,
  not the bytes. Two runs fed different images with the same name report the same hash, against
  `docs/generation-runs.md`'s "its hash half says at a glance whether two runs submitted the same
  graph".

**Why it matters.** `--image` chains scratch candidates, and those are all named `0000.png`,
`0001.png` and so on (`run.rs:468`). Two chained mesh runs from different image runs that pick the
same index upload the same server name. A job still queued, behind a 485 s TRELLIS run or another
client's work, then reads the second image. Its `run.json` and the accepted mesh's `origin.images`
record the first image's hash. The record is wrong, and no gate can notice.

**Failure scenario.**
1. Run `gen run idol-mesh --image runs/idol-portrait/A/0003.png --no-wait`.
2. Then run `gen run idol-mesh --image runs/idol-portrait/B/0003.png --no-wait` while the GPU is
   still busy.
3. Both meshes are made from B. Run 1's provenance names A's hash.

**Fix.** Upload under a content-addressed name, for example `ludion-<content hash>.<ext>`. Without
`overwrite`, ComfyUI already dedups identical bytes. This also makes `graph_hash` cover the image
content.

### C5 — The `--json` contract holds only on success: on failure, six of the seven verbs print nothing on stdout, and the editor has no way back to a failed run · Medium · [verified]

**Evidence.**
- **The contract.** `docs/generation-runs.md:15` and `docs/generation.md:52` promise exactly one
  JSON object on stdout.
- **The failure paths print nothing on stdout.** Only `gen check` prints an object on failure
  (`gen_cmd.rs:294-304`, `:368-380`). Diagnostics-only error branches:
  - `run` at `gen_cmd.rs:551-556`.
  - `status` at `:637-641`.
  - `fetch` at `:769-774`.
  - `sheet` at `:806-811`.
  - `accept` at `:847-852`.
  - `nodes` at `:34-49`.

  Diagnostics go to stderr as rendered text, so a client gets no codes or pointers.
- **The editor drops the run.** `GenerationView.tsx:174-186` handles `json === null` by showing
  stderr and returning, so it never learns the run folder of a timed-out or failed run. Its
  comment at `:183-185` ("A run that ended non-zero still wrote a folder worth looking at, so the
  diagnostics ride beside the grid") describes a branch that cannot happen.
- **The editor has no recovery verbs.** It never invokes `fetch` or `status` (only
  `check`/`run`/`accept`, `:147`, `:169`, `:203`) and cannot pass `--timeout`.
- **The shapes are untested.** The plan says each verb's object schema is snapshot-tested.
  `crates/ludion-cli/tests/gen.rs` runs only `check`, `sheet` and `accept` with `--json`. The
  `run`, `status`, `fetch` and `nodes` shapes, the editor's main dependency, are untested at the
  CLI level, although the mock server that could drive them exists in `ludion-gen`'s tests.

**Why it matters.** The cold TRELLIS mesh run measured 485 s against a 600 s default timeout
(Status, Wave 2). A colder or larger bake times out in the editor. The human then sees an `L1170`
telling them to run a shell command against a run folder the view never named. The parity ruling
(decision 15) rests on this subprocess contract, and on its failure path the contract is prose.

**Fix.**
- On failure under `--json`, print one object, for example
  `{ "ok": false, "diagnostics": [...], "run": <report or null> }`. Include `dir` and the partial
  report whenever `run.json` was written.
- Add `fetch` (and a timeout field) to the view.
- Drive `ludion gen run/status/fetch --json` against the mock in a CLI test that snapshots the
  shapes.

## Low

### C6 — The recorded seed is wrong whenever the recipe pins a seed or the graph's seed is not a literal `seed`/`noise_seed` input · Low · [verified]

**Evidence.**
- `with_seed` skips pinned seeds and linked seeds, and touches nothing else
  (`workflow.rs:425-445`, `:402-404`).
- `download` labels candidate `i` with `seed_base + job` regardless (`run.rs:463`). The sheet,
  `run.json` and `origin.seed` all inherit that label.
- Nothing warns that a `--count N` run will submit N byte-identical graphs.

**Why it matters.** Two common cases trigger it:

- A recipe override `Sampler: seed: 5` ("an explicit override wins", `docs/generation.md:133`).
- A workflow that feeds its sampler's seed from a primitive node's `value`.

Either way, `--count 8` produces eight identical candidates, seven of them served from cache. They
are labelled seeds 7–14, and an accepted one records a seed the graph never used.

**Fix.** Make `with_seed` report whether it wrote any input. When it wrote none, record the
effective seed as the pinned value, or `null`. In `gen check`/`gen run`, warn when `count > 1` and
no unpinned seed input exists.

### C7 — `checkpoints` only sees loader classes whose name contains `Loader`, and a committed generated mesh already omits one of its models · Low · [verified]

**Evidence.**
- `run.rs:407-425` filters on `class_type.contains("Loader")`.
- `trellis2-img2mesh.json:12-14` loads `birefnet.safetensors` through `LoadBackgroundRemovalModel`.
- The accepted `games/vigil/scenes/meshes/idol-generated/meshes/mesh-0.mesh.yaml` lists four
  checkpoints and omits it.
- Only filenames are recorded, never a model file hash. Decision 13 chose this, but it means an
  updated checkpoint under the same name is invisible.

**Why it matters.** Provenance and the licence trail. Every generated mesh is listed in
`THIRD-PARTY-NOTICES.md` from these model facts.

**Fix.** Record every string input whose name ends in `_name` and whose value ends in a model
extension (`.safetensors`, `.ckpt`, `.pt`, `.pth`, `.bin`, `.gguf`), on any node class. Or check
the value against the `/object_info` combo lists of folder-backed inputs.

### C8 — `prompt` includes negative-prompt encoders, contrary to its documented meaning · Low · [verified]

**Evidence.**
- `run.rs:387-402` joins the `text`/`prompt` input of *every* `*TextEncode*` node.
- The unit test at `run.rs:681-684` pins that the negative ("blurry") is included, ahead of the
  positive prompt in node order.
- `docs/generation-runs.md:115`, the plan, and `ludion-scene/src/generation.rs:187` all say
  "positive-conditioning encoder".
- `CLIPTextEncodeSDXL` (`text_g`/`text_l`) contributes nothing.

**Why it matters.** A reader of an origin block sees the positive and negative prompts merged into
one unlabelled string, possibly negative first. The vigil workflows have no negative encoder today,
so no committed sidecar is affected yet.

**Fix.** Follow the graph's edges: take an encoder's text only when its output reaches a
`positive` input. Alternatively, record a `{title: text}` map, and fix the docs or the code so the
two agree.

### C9 — Multi-file jobs break "a candidate's index and its seed are the same fact" · Low · [verified]

**Evidence.**
- `collect_outputs` (`client.rs:552-588`) takes every `images`/`3d` entry of every node, including
  `type: "temp"` PreviewImage files.
- `classify_output` treats `PreviewImage` as an image output (`workflow.rs:738-743`).
- `download` makes each file its own candidate (`run.rs:464-479`).

**Why it matters.** A graph with `batch_size: 2`, or a `PreviewImage` beside `SaveImage`, doubles
the candidates: indices 0 and 1 share one seed, and the sheet shows previews as candidates.
`docs/generation.md:133-135` states the one-to-one rule without that caveat.

**Fix.** Skip `type: "temp"` outputs. Record a `batch_index` per output. Either document the
many-per-job case or warn about it in `gen check`.

### C10 — `gen check`'s live pass silently replaces a malformed address with the loopback default · Low · [verified]

**Evidence.**
- `gen_cmd.rs:340` uses `server_url_or(url)`.
- `server_url_or` (`gen_cmd.rs:389-393`) maps any `resolve_url` error to `DEFAULT_COMFY_URL`.
  Its comment, "reads the same as an unreachable server", is not what happens: the default
  address is then asked.

**Why it matters.** A user means a remote server and types `--url gpu-box:8188`, missing the
scheme, or sets a malformed `LUDION_COMFY_URL`, while a local ComfyUI is running. `gen check` then
validates against the *local* `/object_info` and can print `live: ok`. The malformed-address
diagnostic is never shown. `gen run` with the same flag does refuse.

**Fix.** Report `resolve_url`'s `L1167` as the live verdict (`skipped`), the way an unreachable
server is reported.

### C11 — Several failures that are not "unreachable" are reported as `L1167` "nothing answered … start ComfyUI" · Low · [verified]

**Evidence.**
- `resolve_url` accepts `https://` (`client.rs:58`). The workspace builds `ureq` with
  `default-features = false` (`Cargo.toml:143`), so there is no TLS: ureq 3.4.2 connects over TCP
  and then fails `Error::TlsRequired`. `send` maps every transport *and body-read* error to
  `unreachable()` (`client.rs:488-495`).
- The same message, with "start ComfyUI on that machine", is printed for an HTTPS address, for a
  `/view` body over the 512 MiB cap, and for a large download outliving the 60 s global timeout.

**Why it matters.** The diagnostic sends the reader after the wrong cause (Pillar 5).

**Fix.**
- Refuse `https://` in `resolve_url` with a message saying TLS is not built in. Alternatively,
  enable a TLS feature.
- Map body-read errors to `L1168` with the actual cause.
- Give `/view` a per-request timeout sized for downloads.

### C12 — After a ComfyUI restart, `gen status` reports jobs "pending" forever and `gen fetch` says they "have not finished" · Low · [verified]

**Evidence.**
- `status` (`run.rs:294-302`) and `fetch` (`run.rs:323-347`) treat "no history entry" as "still
  running".
- ComfyUI keeps its queue and history in memory, so a restart loses both.
- `status` fetches `/queue` but never cross-checks it.

**Failure scenario.** A `--no-wait` run is submitted and the server restarts. `fetch` now returns
`L1170` with "`gen status` says where they are in the queue". `status` says "not ready, pending:
…" indefinitely.

**Fix.** A job with no history entry that is absent from both `queue_running` and `queue_pending`
is *lost*. Say so, and point at re-running the recipe.

### C13 — Two runs of the same graph within one second share a run folder and overwrite each other · Low · [verified]

**Evidence.**
- The run id is `<UTC second>-<graph hash>` (`run.rs:219-220`).
- `create_dir` is `create_dir_all`, which succeeds on an existing folder (`run.rs:226`,
  `:613-615`).
- Candidates and `run.json` are written with `std::fs::write` (`run.rs:469`, `:496`).
- `graph_hash` is taken at the base seed, so `--count 4` and `--count 8` of one recipe collide too.
  C4 adds identical-name image uploads to that.

**Why it matters.** Two concurrent invocations interleave their `0000.png` … and the last
`run.json` wins. Examples: two agents, a script loop, or the editor's Generate racing a shell
`gen run`. The id's "collision-free" claim (`run.rs:8-10`) does not hold within a second.

**Fix.** Create the folder with `create_dir` and fail or suffix on `AlreadyExists`, or append a
short random or PID component.

### C14 — Stale docs and message text · Low · [verified]

- `docs/generation-runs.md`'s verb table says `gen sheet --json` prints "the sheet path and its
  cell geometry". It prints `{run_id, sheet, cells}`, where `cells` is a count
  (`gen_cmd.rs:792-796`).
- Three string literals were wrapped without a trailing `\`. Each message therefore carries a run
  of about 18 spaces mid-sentence: `run.rs:344` (`fetch`'s help), `workflow.rs:334` and
  `workflow.rs:339` (`L1217`'s message and help).
- `lib.rs`'s failure-taxonomy table lists `L1162`–`L1172` and omits `L1161` and `L1217`, both of
  which this pipeline raises.
- `run.rs:8-10` calls the run id "collision-free" (see C13). `client.rs:45` says `https://` is a
  valid address (see C11).

## Checked and healthy

- **Server filenames never become paths.** Downloads are written as `<index>.<ext>`
  (`run.rs:468`). `Path::extension` reads only the last component, so a hostile `filename` with
  `..` or separators cannot escape the run folder. `filename`, `subfolder`, `type` and the prompt
  id are percent-encoded into the query (`client.rs:756-767`). The multipart filename's quotes are
  escaped.
- **Prompt injection into workflow JSON.** Overrides are inserted as `serde_json::Value`s and
  serialized by serde (`workflow.rs:751-758`, `to_value`), so quotes, backslashes and newlines are
  escaped correctly. There is no string templating anywhere.
- **Request determinism.** For the same recipe, seed and uploads, the graph bytes are identical:
  nodes are in id order and `graph_hash` is over key-sorted canonical JSON. Only `client_id` (the
  run id) differs between submits.
- **Bounded inputs.** Responses are capped at 512 MiB, and every HTTP call has a 60 s global
  timeout. PNG decode refuses more than 8192² pixels (`ludion-assets`). Both follow paths honor
  `--timeout`, and the socket read timeout is re-armed per frame.
- **The address stays out of artifacts.** It is not in `run.json`, provenance, or text output when
  it came from the environment (`client.rs:501-517`). The editor host owns `--url`/`--json`,
  allowlists the seven verbs (`generation.rs:62-86`), and never persists the address.
- **Accept never overwrites.** Image and sidecar existence are checked before any write. A mesh
  destination must be absent or empty, and every mesh document is re-parsed before the single
  import write. The image is re-encoded through the canonical `encode_png`, so the server's
  ancillary chunks are dropped.
- **Error UX.** A `/prompt` 400's `node_errors` are reprinted node by node with input and details.
  `execution_error` names the node, its class and the message. `L1166` lists every title, and
  `L1164`/`L1165` suggest the nearest installed class or option. The offline half of `gen check` is
  CI-safe and decides the exit code.
- **The mock suite is a real gate.** It is a real `TcpListener` HTTP/WebSocket server driving the
  real ureq/tungstenite client: the happy paths (image and mesh), one case per code, the polling
  fallback, and `--no-wait` + `fetch`. It is not a trait mock. The one structural blind spot is the
  frame replay noted in C2.
- **Ignore rules and codes.** `generation/runs/` is in both `.gitignore` and `.loreignore`.
  `L1161`–`L1172` and `L1217` are registered in `codes.rs`.
- **Both document kinds are inert to the engine.** `kind: generation` and `kind: origin` are only
  `ENGINE_KINDS` entries, and nothing in a scene names a recipe or a run.

## Suggested order of work

1. **C1.** Snapshot `prompt`/`inputs` into `run.json` and build provenance from the report. It is
   small, and it fixes the one committed-artifact defect.
2. **C2.** Open `/ws` before submitting, plus a `/history` sweep, and teach the mock to drop
   pre-connect frames.
3. **C3 with C12.** Per-job outcomes in `run.json`, a `partial` status, and a "lost" verdict from
   `/queue`.
4. **C4.** Content-addressed upload names. This also corrects `graph_hash` and narrows C13.
5. **C5.** A failure object under `--json`, `fetch`/timeout in the view, and CLI shape tests against
   the mock.
6. **C6–C11, C13, C14.** Provenance and labelling accuracy, then the message and doc fixes.
