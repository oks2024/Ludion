# Crate graph — edges

**Scope:** the in-workspace dependency edges as the manifests declare them, the optional-feature
shapes, and which third-party stacks stay confined to which crate. The inventory and the boundary
rules are `ludion devdocs crate-graph`; the clippy split that rides on this graph is `ludion devdocs determinism`.

## Layout

(`check.mjs --fix` runs it too) and checked by `lists-in-step`; never hand-edit it. Reading it:
`→` = depends on (in-workspace names on the right drop their `ludion-` prefix, then the
third-party crates in `[...]`); `dep(feat)` = optional, switched on by that feature of the row's
crate; `dep{f}` = an in-workspace dependency requested with feature `f`; `dev:` / `build:` rows
list dev- and build-dependencies; `←` rows invert the edges for the confined stacks and for each
`crate/feature` an in-workspace crate opts into, over normal and optional edges only.

## Rules

`ludion` is the one **library** crate allowed to depend on both `ludion-engine` and `ludion-server` —
it unites them behind a game's `main` (the engine still never depends on the server). Games depend only on the
facade at runtime, and on `ludion-testkit` (+ `ludion-engine` for `replay_hashes_with`) as
dev-dependencies. `games/*` are workspace members; `examples/*` are not.

**wgpu is always in the tree.** The embedding core renders, so the facade names it unconditionally
(`embed::Surface`, `ffi`), and a `--no-default-features` facade reaches it through engine → renderer
too. Only four stacks are gated: `tokio` (through `ludion-server`, the facade's `wire`), `winit` and
`gilrs` (through `ludion-window`, the facade's `window`; winit's event loop also runs in the
facade's `present.rs`), and `notify` (`ludion-assets`' opt-in `watch`, which the facade asks for
only under `wire`). The feature-less facade, the mobile shape in `Plan/ios-target.md`, carries none
of the four; `scripts/mobile-check.mjs` asserts it. The crates in the `no wgpu in the tree` row are
what keeps `cargo check` fast for content and sim work.

The block lists every dev-dependency; two are worth explaining, since the normal graph forbids
nothing about them: `ludion-server → client, testkit` (the over-the-wire SSIM/parity tests live in
the server's integration tests), and `ludion-testkit → ludion` (the gallery cycle example's host,
`examples/character_cycle.rs`).

The `editor/` Tauri + React app and `ludion-mcp` both ship; the MCP adapter derives its whole tool
catalog from `protocol_schema()`, so it cannot hold an editor-private endpoint (the parity gate).
The architecture doc's graph (§2) describes the *end state* — e.g. it lists
`ludion-testkit → engine, client`; the current manifests intentionally lack the testkit → client edge
(the wire tests sit in `ludion-server`'s dev-deps instead).

Where shared logic goes: domain logic lives in the owning `ludion-*` crate; `ludion-engine` is
glue (`dispatch.rs` routing only); `ludion-cli` modules are thin `run()` wrappers.
The builtin component registry is defined once in `ludion-engine` and shared downward.
