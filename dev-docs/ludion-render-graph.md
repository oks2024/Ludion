# ludion-render-graph

**Scope:** The engine's one rendering abstraction: a declarative frame graph (virtual resources + passes with read/write declarations) scheduled deterministically on CPU, then executed on a headless wgpu device with blocking PNG readback. Covers pass declaration, scheduling/aliasing, `dump-graph`/`dump-timings` JSON, the `PassRecorder` seam, and readback. The render pipeline that builds on this graph is `ludion-renderer`; golden-image comparison of its output is `ludion-testkit` / `golden-testing`.

## Spokes
- `ludion devdocs render-graph-gpu` — execution, readback, timings, GPU error policy, present.

## Layout
- `crates/ludion-render-graph/src/lib.rs` — crate docs, re-exports, `build_graph(w, h)` (the fixed 4-pass proving graph: gradient → vignette → bleed → present).
- `crates/ludion-render-graph/src/graph.rs` — `RenderGraph`, `ResourceDecl`, `ResourceKind` (Transient/Output), `PassDecl` (a `color` target list, an optional `depth` attachment and `storage` write), `PassKind` (Gradient / Vignette / External / **Compute**), and the `add_*pass*` constructors: `add_external_pass_with_depth` (a colour *list* plus a depth attachment: the scene and transparents passes; an empty list is the depth-only shadow pass), `add_external_pass` (colour list, no depth: `reflections`), `add_external_compute_pass` (storage only — `gi_inject`).
- `crates/ludion-render-graph/src/resource.rs` — wgpu-free descriptors: `ResourceId`, `Extent2d`, `TextureFormat` (`R32Float` is single-channel and unfilterable, for depth pyramids; `Rgba32Float` is unfilterable, a compute pass's exact-f32 table), `TextureUsage` (`StorageBinding` — a compute pass's writable output), `TextureDesc` (constructors `color`/`hdr_color`/`r32_float`/`rgba32_storage`/`depth`/`sampled_depth`/`hdr_storage_volume`, `alias_compatible`).
- `crates/ludion-render-graph/src/schedule.rs` — `schedule(&RenderGraph) -> Result<Schedule, Diagnostic>`: read validation (L2002), Kahn topo sort with declaration-order tie-break (cycle = L2001), lifetime computation, greedy transient aliasing (`Aliasing`, `PhysicalTexture`).
- `crates/ludion-render-graph/src/execute.rs` — the only public-API wgpu surface: `Gpu::request` / `Gpu::request_for_surface` (L2003/L2004; one private `request_from`, the compatible surface the only difference), `render_to_image` (built-in kinds), `Gpu::execute` + `PassRecorder`/`RecordedPass` (external passes), `RenderedImage`, `allocate_physicals`.
- `crates/ludion-render-graph/src/readback.rs` — blocking `read_texture_to_image` (L2005) and the persistent 3-deep async `StreamReadback` ring (`Gpu::render_frame` + `FrameSinks` records the passes once and fans out to the readback ring and/or a present target; `render_streamed` is the both-defaults wrapper, `try_collect` drain-only, `Gpu::render_frames_via_ring` measurement seam); 256-byte row-padding handling.
- `crates/ludion-render-graph/src/blit.rs` — the window blit both presenters share (`ludion-window`'s viewer too): `BLIT_WGSL`, `Blit`, `SurfaceSetup` (format/alpha choice, pure), `surface_unavailable` (L2007).
- `crates/ludion-render-graph/src/present.rs` — `PresentTarget` (surface + `Blit`, built with `Gpu::request_for_surface`'s adapter) and `PresentSize` (an `Arc<AtomicU64>` the window thread writes resizes into); `present()` blits the resolved output texture letterboxed via `ludion_core::letterbox`.
- `crates/ludion-render-graph/src/dump.rs` — `Schedule::dump_graph_json()`: canonical, byte-stable JSON (passes, resources, schedule, aliasing).
- `crates/ludion-render-graph/src/timings.rs` — `Gpu::dump_timings_json(schedule, output, Option<&dyn PassRecorder>)`: per-pass GPU ms via timestamp queries, graceful `{"timestamps_supported": false}` fallback; the shared `PassTiming` (name + optional `gpu_time_ms`).
- `crates/ludion-render-graph/src/pass_timing.rs` — `PassTimingRing<S>` (`Gpu::new_pass_timing_ring`): the non-blocking 3-deep counterpart of `dump_timings_json` for the live loop, armed per frame via `Gpu::render_streamed`'s `timing` argument and drained by `try_collect_timings`.
- `crates/ludion-render-graph/src/png_io.rs` — `RenderedImage::encode_png` / `write_png` (L2006), deterministic (IHDR/IDAT/IEND only, no timestamped chunks).
- `crates/ludion-render-graph/src/shaders/{gradient,vignette}.wgsl` — the proving graph's shaders.
- `crates/ludion-render-graph/tests/` — `dump_graph_snapshot.rs` (byte-level snapshot vs `tests/snapshots/dump_graph_64x64.json`), `gpu_render.rs` (adapter-gated determinism tests that skip without a GPU).

## Rules
- **The declarative half names no wgpu type** (`graph`, `schedule`, `resource`, `dump`). Formats/usages/extents are this crate's own enums; passes reference `ResourceId` handles. wgpu appears only in `execute`, `readback`, `present`, `timings`. This is the deliberate ash-migration seam (`engine-architecture.md` §2): no backend traits, no generic resource types — a backend swap replaces the execution layer wholesale.
- **The offscreen target is the source of truth.** Every pass draws into it; a present target is an *additional* sink that blits it, never a render target of its own — goldens, screenshots and the frame stream are byte-identical with or without a window, and `FrameSinks { present: None }` submits the commands it always did. Adapter selection is one path (`request_from`): high-performance hardware first, then `force_fallback_adapter: true` (WARP/llvmpipe). The headless `Gpu::request` walks `VULKAN|METAL` (hardware only) → `PRIMARY` → `all()`, and a `WGPU_BACKEND` pin is the only tier; surface hosts build their instance with `Gpu::instance()` (`PRIMARY`) and keep the fallback retry, `request_for_surface` only constraining it to an adapter that can present.
- **Deterministic scheduling.** Kahn topo sort; among ready passes the earliest-declared runs first. Same graph → same order → same aliasing → byte-identical `dump_graph_json`.
- **Output resources never alias** — they must survive to be copied out. Only `ResourceKind::Transient` participates; alias-compatibility is extent + format equality (usages are unioned).
- **A pass writes any number of color targets (`PassDecl.color`, one extent between them and the depth attachment), at most one depth attachment, and at most one storage texture.** All are optional: a color-only post pass, the renderer's scene pass (colour list + depth — `add_external_pass_with_depth`), a depth-only pass like the shadow pass (`add_external_pass_with_depth` with an empty colour list), and a **compute** pass (`add_external_compute_pass` — storage only, no attachment at all) are all expressible. The scheduler treats a depth write and a storage write exactly like a color write for ordering — a later pass that samples either (e.g. the scene pass sampling a shadow map, or sampling `gi_inject`'s volume) orders after the pass that wrote it. Built-in kinds derive reads from `PassKind::intrinsic_reads()`; every `add_external_*` constructor takes them explicitly instead (stored on `PassDecl.reads`).
- **Transients can be mipped.** `ResourceId::mip(level)` names one level, and the pass attaches a view of just that level; a read of the bare handle needs every level written (L2002 names the missing `name@mipN`). Mip count joins extent and format in alias-compatibility. The dump spells a single level `name@mipN` and adds a `mips` field only to mipped resources, so an unmipped graph's dump is byte-identical to before.
- **Passes writing overlapping subresources run in declaration order** — a later writer orders after the earlier one (write-after-write) and after the earlier one's readers (write-after-read), so a pass that adds into a target another pass cleared stays behind it. A read with at most one overlapping writer, or whose writers touch disjoint mips, orders by the read alone. Declaring them in the wrong order produces a wrong picture, not a cycle.
- Every failure is an `L####` `Diagnostic`: L2001 cycle, L2002 unwritten read, L2003 no adapter, L2004 device failed, L2005 readback failed, L2006 PNG IO, L2007 presentation unavailable, L2010 GPU rejected the work, L2011 device lost (L2012, a bad extent, is the renderer's).

## Verify
```
cargo test -p ludion-render-graph            # unit + snapshot tests, no GPU needed for scheduling/dump
cargo test -p ludion-render-graph --test gpu_render   # real adapter render; skips (prints why) without one
cargo run -p ludion-cli -- dump-graph --scene examples/gallery/sprites.yaml --width 1920 --height 1080
cargo run -p ludion-cli -- explain L2001     # every code above resolves in the code table
```
The doc examples in `lib.rs`/`graph.rs`/`schedule.rs` are runnable: `cargo test -p ludion-render-graph --doc`.

## Gotchas
- `ludion dump-graph` prints the **renderer's** frame graph from `ludion-renderer::dump_frame_graph_json`, not this crate's proving graph, and it is much larger than the four-pass example above: fifteen external passes for a plain scene (`scene`, `reflections`, `transparents`, `bloom_threshold`, five `bloom_down`, five `bloom_up`, `composite`), plus the scene's `PostChain` and render scale: `shadow`, `prepass`/`ssao`/`ssao_blur`, `shafts`/`shafts_blur`, `dof_coc`/`dof`, `resolve`/`upscale`, `overlay`; a scene authoring the whole roster schedules twenty-three.
- **The resampling pass is the one renderer pass a scene cannot cause.** Every other conditional pass comes from `PostChain`, which is derived from scene content; `resolve` (above native) and `upscale` (below it) are added by `FrameSize::resample()` — a *client* setting. So the same scene dumps a different pass list at a different `--scale`, and a resource extent alone is not enough to identify a target.
- **Which extent sizes which target is the renderer's rule, not this crate's**, but it is what makes a `dump-graph` resource list readable: only the scene pass's colour and depth targets, the ambient-occlusion prepass's two targets, and `ldr` take the render extent; every other target takes the output extent. A post target that looks "half resolution" is half of the *output*, so at a render scale above 1 it is not half of `scene` — and below 1 it is larger than `scene` outright. `ludion-renderer`'s `graph.rs` module doc is the normative statement.
- `shaders/{gradient,vignette}.wgsl` are reflected and drift-gated by `ludion-shader-bindgen` (their bindings must agree with any same-named struct/resource elsewhere in the workspace), but their CPU-side bindings are **not** generated into this crate — `ludion-shader-bindgen`'s output lives in `ludion-renderer::shader_gen`, one crate above this one in the graph, so a second generated file here would fork the single-reflection model. `execute.rs`'s hand-written BGL for these shaders stays hand-written; see the `ludion-shader-bindgen` topic.
- Determinism claim is per-adapter: same schedule on the same adapter → identical bytes. Across GPUs/drivers only perceptual (SSIM) comparison holds — see `golden-testing`.
- **`RecordedPass::colors()` is empty on a depth-only pass** (a shadow map, e.g.); index it only from a recorder arm you know writes color, and check `colors().is_empty()` otherwise. `depth` is always the right field to reach for a depth-only recorder.
- **Depth and color resources never alias with each other** — `TextureDesc::alias_compatible` requires equal `format`, and `Depth32Float` never equals a color format, so the aliaser can never assign a depth attachment and a color target to the same physical texture.
- `TextureDesc::depth` (attachment-only) and `TextureDesc::sampled_depth` (attachment + texture-binding — the renderer's `scene_depth` and `shadow_map` both take this one, since a depth resource a shader may bind needs the usage) are both `Depth32Float`; picking `depth` for a resource something samples leaves the sampler with nothing to bind. `ludion-renderer::graph.rs` is the reference for which pass gets which.
- **A 3D resource (`depth_slices: Some(_)`) never aliases a 2D one, by the same equality rule as depth-vs-color** — `alias_compatible` compares `depth_slices` too, so a volume like `gi_inject`'s probe lattice never shares a physical texture with a flat target. A volume also can never be an attachment (`add_pass`/`add_external_pass*` panic on one via `require_flat`) or a graph output (`RenderGraph::output` panics: readback produces one 2D image, and a volume has none) — it exists only as a `transient` a compute pass writes and a later pass samples.
- **`add_external_compute_pass` panics if its `storage` resource lacks `TextureUsage::StorageBinding`** — build one with `TextureDesc::hdr_storage_volume`, not `hdr_color`/`color` plus a manually-added usage; the panic names the resource and fires at graph-construction time (otherwise the failure is a cryptic bind-group error at record time).
