# render-graph-gpu

**Scope:** The execution half of `ludion-render-graph`: `Gpu::execute`, the streamed readback ring, pass timings, the GPU error policy and the present path. Declaration, scheduling and aliasing stay in `ludion devdocs ludion-render-graph`.

## Dataflow
Build a `RenderGraph` with `transient`/`output` (returning `ResourceId`s) and `add_pass`/`add_external_pass`. `schedule()` validates reads, topo-sorts passes, computes each resource's `[first_use, last_use]` lifetime over the execution order, then greedily assigns transients (in `(first_use, index)` order) to the first free, alias-compatible physical texture. The resulting `Schedule` is fully inspectable without a GPU — `order_names()`, `physical_texture_count()`, `dump_graph_json()`.

Execution has two paths. `Gpu::render_to_image` runs the built-in pass kinds (the proving graph only) and panics on `PassKind::External`. `Gpu::execute(schedule, output, &dyn PassRecorder)` is the seam `ludion-renderer` uses: per pass, the executor resolves the color target (if any), the depth attachment (if any), and input `wgpu::TextureView`s through the aliasing assignment and hands a `RecordedPass` (label, kind token, optional target view/format/extent, optional depth view, inputs, device, encoder, optional timestamp pair) to the recorder, which owns pipeline selection and `begin_render_pass` (via `begin()`/`begin_clear(color)` helpers, or its own descriptor, e.g. to attach the resolved `depth` view alongside or instead of a color target). Both end in one blocking readback (`device.poll(wait)`), so the returned `RenderedImage` (packed top-to-bottom RGBA8) is exactly that frame.

`dump_timings_json` brackets each pass with descriptor-level timestamp writes at indices `(position*2, position*2+1)`, resolves, reads back, and scales by the queue timestamp period to milliseconds; adapters without `TIMESTAMP_QUERY` get the stable fallback shape, never an error. `render_frame` pipelines up to three `map_async` readbacks through the persistent `StreamReadback` ring — submit a frame + non-blocking-collect every finished readback and deliver the newest (latest-wins inside the ring); when all slots are in flight it waits once and drains the ring (the ~2-frame worst-case live-streaming latency); with `readback: false` it consumes no slot, records no copy and returns `Ok(None)` (the window-only, zero-encode path). `render_frames_via_ring` reuses the same ring as a measurement seam; the CLI and `render.screenshot` use only the blocking path.

`render_frame`'s `timing: Option<&mut PassTimingRing<S>>` argument is the live-profiling seam: `Some` binds that frame's slot query set as the `query_set` every pass's timestamp writes reference, records the resolve + copy into the same encoder, and `map_async`'s the readback after submit; `None` submits exactly the untimed commands (no query set created, no resolve, no allocation). Samples come back out of band through `try_collect_timings(&gpu)`, 1–3 frames late, each carrying the stamp of the frame it measured.

## GPU error policy
No GPU error kills the process. `Gpu` requests `engine_limits()` (the WebGPU floor plus `max_bind_groups: 5` and `max_vertex_attributes: 20`, each raise commented with the content that needs it) instead of `adapter.limits()` (and requests `TEXTURE_COMPRESSION_BC`/`_ASTC` only when the adapter offers them: `Gpu::supports_compressed` and `cook_targets` are the query, by adapter features and never by OS; `cook_target` is its head, and the engine reads the first supported target that has a store), so the 3090 and M4 stop hiding what a floor-only device (iOS) would hit; `MAX_TEXTURE_DIMENSION_2D` (8192) is that floor's texture limit and the renderer's `FrameSize::validate` bound. An uncaptured-error handler and a device-lost callback fill a shared sink; `Gpu::take_fault()` drains it — a loss is L2011 and sticky, validation/OOM messages are L2010 and cleared once taken. Every submitting `Gpu` method (`render_to_image`, `execute`, `render_frame`, `try_collect`, `render_frames_via_ring`, `dump_timings_json`) takes it on entry and exit, and a pending fault replaces the method's result, including an L2005 (the symptom). Submits made straight through `device()`/`queue()` (the GI bake) surface at the next such call. There is no device-loss recovery: the live loop latches no-render and reports the fault to an armed host (`Engine::arm_render_fault_notify`).
A windowed game, a headless host (exit code FAILURE) and the iOS host (through `ludion_ended`)
end with the fault printed. `ludion-window`'s viewer requests its device through
`Gpu::request_for_surface` and takes that device's faults after each submit: a fault is fatal and
ends the viewer. Both presenters cap the swapchain at `MAX_TEXTURE_DIMENSION_2D`
(`blit::surface_extent`, aspect kept).
## Gotchas
- `RecordedPass` timing contract: a recorder that opens its own `RenderPassDescriptor` must pass `pass.timestamp_writes()` in it or its pass reports ~0 ms; a recorder that opens several render passes for one graph pass must attach the pair to exactly one (wgpu forbids writing a query index twice). **`RecordedPass::begin_compute()` attaches the timestamp pair for you** — it is the compute counterpart of `begin()`/`begin_clear()` and is almost always the right call; a recorder that instead builds its own `ComputePassDescriptor` (e.g. to pass extra options wgpu's descriptor needs) must pass `pass.compute_timestamp_writes()` in it, or the pass silently reports ~0 ms exactly like the render-pass case.
- **`PassTimingRing` drops samples on purpose.** With all `DEPTH` (3) slots in flight it skips the frame's timing rather than blocking for a slot — the opposite of `StreamReadback`, because a profiler that stalls the render loop falsifies its own numbers. A graph above `PassTimingRing::MAX_PASSES` files a sample naming its passes with no times, and `try_collect_timings` returns no `Result`: a failed map costs one sample, never a frame — "no sample this frame" is normal, not an error.
- **The present fails loudly only on a dead surface.** `Fifo`, run on the presenter thread (`Plan/display-paced-present.md` decision 4): the acquire blocks to the display's rate and the sim thread never waits on it; a lost/outdated/timed-out/occluded swapchain silently skips one frame (the next reconfigures), and only a surface validation failure raises `L2007` — a dead surface must end the host, not paint black forever: the live loop latches no-render, reports it to the host once (`Engine::arm_render_fault_notify`), and the windowed host stops with L2007 printed. Physical *color* textures carry `TEXTURE_BINDING` beyond what their resources declared so the blit can sample the output; `dump-graph` prints the declared usages and is unmoved.
- `TARGET_FORMAT` in `execute.rs` is `Rgba8UnormSrgb` and must match the proving WGSL targets and readback; external pipelines instead match against `RecordedPass::colors()[i].format`.
- Readback rows are padded to `COPY_BYTES_PER_ROW_ALIGNMENT` (256); `RenderedImage.rgba` is already unpadded — never index the staging buffer directly.
- `RenderGraph::output` may be called more than once, but only the resource passed as `output` to `render_to_image`/`execute` is read back.
- **On the streamed path a pass's target is not zeroed — it holds the previous frame's pixels.** `render_streamed` allocates the graph's physical textures once and reuses them for every later frame (`PhysicalCache`, keyed on the whole `Aliasing`, held by the `StreamReadback` ring and rebuilt when the aliasing moves). So a pass must clear its attachment or cover it whole; the renderer's one `LoadOp::Load` pass (`overlay`) is legal only because its unblended full-target blit writes every texel. `egress.rs`'s `needs_gpu_streamed_frames_survive_physical_texture_reuse` pins it: the first streamed frame draws into fresh textures and every later one must match it. The blocking paths (`execute`, `render_to_image`) still allocate per call. `LUDION_SUBMIT_TRACE=1` prints a per-segment breakdown of `render_streamed` (ring occupancy, stall count, allocate/record/submit/collect) to stderr — the instrument for a `submit_ms` that spikes, since the report deliberately carries no `readback_ms`.
