# Determinism

**Scope:** The tiered-determinism contract: which rules bind sim-side crates, the per-crate
`clippy.toml` denylist mechanism that enforces them, the CI canary that proves the mechanism fires,
and `ludion sim-hash` / `WorldHash` as the verification primitives. The hash's byte-level definition
and the tick loop are `ludion devdocs ludion-sim`; which crates are sim-side vs host-side is
`ludion devdocs crate-graph`; perceptual image verification is `ludion devdocs ludion-testkit`. The
per-subsystem "recorded vs regenerated" contracts live with their mechanisms
(`ludion devdocs engine-replay`, `ludion devdocs engine-content-kinds`). A dependent game's own
`Cargo.lock` is not covered by these gates: `ludion docs verify-loop`.

## Layout

- `crates/<crate>/clippy.toml` — one per crate (and per game, and the `ludion new` template): a hand-written header stating the tier and why, then the list generated by `scripts/clippy-denylist.mjs`.
- `scripts/clippy-denylist.mjs` — the one source of every denylist: the rule groups, the `sim`/`strict`/`permissive` tiers and the crate → tier map (`CRATES`). `--write` regenerates; `scripts/lists-in-step.mjs` (in `check.mjs` and CI) fails on a hand-edited or stale file and on a workspace crate with no tier.
- `crates/ludion-core/src/collections.rs` — `StableMap`/`StableSet` (BTree-backed), the mandated `HashMap`/`HashSet` replacements.
- `crates/ludion-core/src/rng.rs` — `DeterministicRng` (PCG32), the one RNG, plus `WorldSeed` and the two derived-stream constructors.
- `crates/ludion-core/src/par.rs` — `par_chunks` / `par_map_chunks` / `ordered_reduce` plus the thread-count controls: the only sanctioned parallelism on the sim path.
- `crates/ludion-ecs/src/par_query.rs` — `World::par_for_each` / `par_join_fold`, the ECS entry points onto `par`.
- `crates/ludion-core/src/math.rs` — pure-Rust `libm` wrappers for every `f32` transcendental method (plus an `f64` submodule).
- `crates/ludion-core/src/time.rs` — `SimTime`, `FrameIndex`, `TickRate`: how time reaches systems.
- `crates/ludion-sim/tests/determinism.rs` — in-process double-run suite (CI layer 1).
- `crates/ludion-cli/tests/sim_hash.rs` — cross-process hash comparison (CI layer 2).
- `crates/ludion-cli/tests/replay.rs` — replay round-trip (CI layer 3).
- `crates/ludion-engine/src/bisect.rs` — keyframe-drift and two-run localization (`ludion devdocs engine-replay`).
- `games/{vigil,breakout}/tests/thread_identity.rs` (vigil's files are private, Lore-only, absent from a public clone) — the 1/2/8-thread hash-identity gate (`Plan/deterministic-job-system.md` J0) over the named replay corpus (`games/vigil/{run,stress}.lrp`, `games/breakout/run.lrp`); every test is `#[ignore]`d and rides `--full`/CI, not the default lane.
- `.github/workflows/ci.yml` — `cargo clippy -- -D warnings` on Windows + macOS, plus the `denylist-canary` and `thread-identity` jobs; `ci/scripts/denylist-canary.mjs` is the canary's one copy.
- `rust-toolchain.toml` — pins rustc; hashes and goldens are versioned against the pin.

## Rules

The tiers: **CPU-side sim state is bit-exact** (fixed timestep, seeded RNG, reproducible ticks);
**images gate on perceptual comparison** (SSIM + tolerance), with bit-exact image goldens only on
pinned GPUs. The pinned tier is **per (OS, GPU)** — Windows (RTX 3090) and macOS (Apple M4), each with
its own blessed set in a per-OS subdirectory resolved by `ludion_testkit::platform_dir` (`L2205` on
any other OS). Cross-OS bit-exactness of the *sim* is measured in CI as a signal, not a gate; the
guarantee is per (target, pinned toolchain). The measurement that exists: the Windows/x86_64-recorded
`run.lrp` sessions committed for `games/breakout` and `games/vigil` (private, Lore-only) replay to identical WorldHash
traces on Apple M4/arm64. To re-take the same-machine reference, run
`ludion sim-hash --scene examples/gallery/lights.yaml --frames 600` and the same against
`examples/gallery/breakout-mock.yaml` on each pinned box and compare — never transcribe the hashes
into a doc, where they rot silently against a toolchain bump.

For all sim-side crates (`ludion-core`, `-ecs`, `-scene`, `-assets`, `-sim`, `-engine`, `-cli`, and
every game crate):

1. **No std `HashMap`/`HashSet`** — use `ludion_core::collections::{StableMap, StableSet}`
   (deterministic iteration order).
2. **No wall clock in sim** — `Instant::now`/`SystemTime::now` and `Instant::elapsed`/`SystemTime::elapsed` banned; time arrives only as
   `SimTime`/`FrameIndex` parameters (`SystemCtx`).
3. **One seeded RNG** — `DeterministicRng` as a world resource, seeded from the scene/replay header,
   with the seed beside it as `WorldSeed`; never `thread_rng` (no `rand` dependency exists in the
   workspace at all). Extra streams come from the two sanctioned constructors only, never from
   hand-seeding.
4. **Transcendentals via `ludion_core::math`** (pure-Rust libm; platform libm differs across OSes).
   Plain arithmetic is fine — Rust does not auto-contract FMA — and so is most of glam: the workspace
   turns on glam's `libm` feature, so its scalar-path trig (`Quat::from_rotation_*`, `from_euler`,
   `Vec2::from_angle`) is pure-Rust too. Not all of it: on x86_64 `Quat::slerp` uses glam's own SSE2
   sine, and the 4-lane `Quat`/`Vec4` dot products sum in a different order from NEON, so
   `Quat::{slerp, lerp, normalize, length*, dot, angle_between, rotate_towards}` and the `Vec4`
   dot-based methods are banned in the `sim` and `strict` tiers — write them component by component
   in a fixed order, as `ludion_core::math::rotation` does. Also banned: `Vec3A::normalize` (SSE2
   divides, NEON multiplies by the reciprocal length) and `Mat4::{inverse, determinant}` (different
   `dot4` order / SIMD lowering) → `ludion_core::math::mat4_inverse` / `mat4_determinant`. Checked
   and allowed (same op sequence on both backends): `mul_quat`, `Vec3A` dot/length/cross/
   `try_normalize`/`normalize_or*`, and `Mat3A`/`Affine3A`/`Mat2` inverse. `sqrt` (IEEE, correctly rounded) and the
   exact ops (`abs`, `floor`, `mul_add`, `to_radians`) stay allowed.
5. **Systems run sequentially in explicit registration order.** There is no parallel scheduler and no
   system runs concurrently with another. Data parallelism *inside* one system is sanctioned only
   through `ludion_core::par` and its ECS entry points. Ad-hoc `std::thread` spawns/scopes and rayon
   stay banned in sim crates, except rapier's internal scheduler on the pool `ludion-physics` owns,
   sized `par::threads()` (`Plan/deterministic-job-system.md`).
6. **Deterministic entity allocation** — free-list pop order defined and conformance-tested in
   `ludion-ecs`.

Host-side crates (`ludion-render-graph`, `ludion-renderer`, `ludion-testkit`) are exempt: their
`clippy.toml`s are deliberately empty (wall clock is *required* for GPU timings; std hash containers
are fine in GPU glue).

**Chunk size is part of the determinism contract; thread count is not.** A reduction's last bits may
legitimately depend on `chunk_size` (a different grouping is a different sum), so changing one at a
call site is a hash-moving edit handled like any other — the `LUDION_BLESS=1` re-bless / re-record
procedure. The same input at 1, 2 or 8 threads is **bit-identical**, and that invariance is what the
gate proves.

**A default worker count must be one the identity gate proves** — hence the cap at
`par::AUTO_THREAD_CAP` (8), the top of the gate's 1/2/8 range. A bigger machine can ask for more
explicitly but never lands there by accident. And **the count is per-machine, so it lives in the
environment**, never in a committed file: thread count is a property of the box, not of the project. A
host's `--threads` beats `LUDION_THREADS` (and is not validated against it, so a flag still works
where the variable is malformed); a malformed variable with no flag is `L0014` and refuses to start,
because a silently ignored setting means running at a count nobody chose.

Additional invariants: never `Arc<Mutex<World>>` (the driver owns the world); flaky tests are P0 bugs;
toolchain bumps are deliberate events that re-bless hashes.

## Dataflow

Enforcement (per-crate clippy denylists, the canary), the three-layer hash harness, `ludion sim-hash` verification and the thread-identity gate: `ludion devdocs determinism-enforcement`. Derived streams and deterministic parallelism: `ludion devdocs sim-parallelism`.

## Gotchas

- `clippy.toml` is resolved per *crate directory* — a new `ludion-*` crate gets **no** denylist until
  you copy one in. Creating a crate without one silently opts it out; copy
  `crates/ludion-sim/clippy.toml` (strict) or `crates/ludion-renderer/clippy.toml` (permissive, with a
  header explaining why) and adapt the comments.
- The denylist bans the *type path*, so `std::collections::HashMap` is caught but a re-export or
  `hashbrown` would not be. New dependencies on sim-side crates need a manual determinism review.
- `serde_json`'s `preserve_order` feature is **load-bearing** (workspace `Cargo.toml`): it keeps JSON
  object keys in struct-declaration order for the canonical scene writer. Do not remove it;
  `WorldHash` is immune to key order because its encoder sorts keys explicitly.
  `float_roundtrip` is load-bearing too: without it a parsed `f64` may land one ULP off, and an
  `f64` in hashed state (`ClipAnchor.ticks`) that crossed JSON text (a snapshot, a keyframe)
  would move the hash.
- `ludion-cli` and `ludion-engine` are strict even though they touch the renderer — they sit on the
  sim-side tree. Don't "fix" a denylist error there by weakening the list; route the offending code to
  a host-side crate instead.
- Wall-clock *pacing* is legitimately allowed one layer up (a live scheduler deciding when to call
  `advance()`); the ban is on wall clock reaching sim *state*.
